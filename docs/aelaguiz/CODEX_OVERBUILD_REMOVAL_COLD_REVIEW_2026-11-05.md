# Cold review of the Codex overbuild removal

**The approved overbuild cuts pass this review, with no blocking finding.** The changes remove unnecessary launch dependencies and historical settings replay while retaining the privacy controls and native credential coordination that were meant to stay. They introduce no broker, service, compatibility mode or new policy framework.

This review covers [removing unnecessary Codex privacy gates and recovery machinery (#18)](https://github.com/aelaguiz/aimgr/issues/18), against PR head `7c4eccb9a00ad62a3119f35ec9531091aed97f9e`. The implementation was an uncommitted working-tree diff when inspected. It does **not** fix the broader vendor file-read policy or outside-project screenshot failure tracked in [workflow adoption (#16)](https://github.com/aelaguiz/aimgr/issues/16). This verdict establishes completion of the overbuild cuts, rather than compatibility of the entire privacy milestone.

**The cuts follow the original recommendations.** I independently inspected the changed implementation and its callers, the issue's acceptance criteria, the amended plan, the affected test assertions and the unchanged official source. These are the substantive results:

The [plan amendment](CODEX_PRIVACY_PROXY_PLAN_2026-11-01.md#L24) accurately records these decisions. It also corrects the earlier conflation of approved account-directory isolation with approval of every host-path denial. Private account/environment identity, local primary credentials, native refresh locks, targeted metadata controls, exporter shutdown, ordinary tool access and the necessary MCP conversion transaction remain in place. The small optional suggestion to combine the worktree executable was conditional on a real reduction in complexity; leaving it alone is not an omitted requirement.

**Settings recovery remains bounded without dropping the established interruption cases.** The changed code still journals before exchange, identifies an exchanged staged inode, preserves uncertain source publication, keeps the old merge baseline when a race is detected, and commits the resulting baseline before retiring settled recovery inputs. Consuming a detected race is different from continuing to watch the old inode indefinitely. The tests retain the source/view exchange races, source-winning same-key conflict, seven interruption boundaries, relative-path writeback and permission recovery. The added repeated-edit check asserts that successful alternating atomic and in-place saves leave neither replay history nor displaced files. Actual native marketplace writes and native settings edits matter here because synthetic atomic saves alone would not establish compatibility with the in-place upstream writer.

**Test evidence.** I inspected the copied final Linux and Mac receipts and the exact native verification runner. The public record is the [overbuild acceptance evidence](CODEX_OVERBUILD_REMOVAL_ACCEPTANCE_2026-11-05.md). The ten native stages completed successfully on both platforms: helper boundary, installed artifact admission, candidate installation, pending-maintenance gate, native configuration/database inputs, utility commands, native settings edits, native relative paths, process inventory and MCP maintenance. Both final admission runs passed all 25 tests with no skip. The utility receipts confirm stock/protected socket echo and actual marketplace removal; the settings receipts confirm native writeback and both-account relative paths. Both maintenance outputs confirm complete credential conversion, conflict preservation, native logout without resurrection and all seven SIGKILL recovery boundaries.

The Mac full-suite receipt shows 1,000 passing tests and 16 skips out of 1,016 tests, with zero failures. The broader Linux run recorded 957 passes, 39 failures and 19 skips out of 1,015 tests because CLI launches overlapped the synthetic conversion fixture and saw its real pending marker. That run is not a clean full-suite pass. I inspected the subsequent receipt: all 108 tests in the affected files passed after the fixture finished, with zero failures or skips and no product change. Earlier harness failures from the wrong Node/PATH and missing loopback fixtures are not product fixes or evidence of unchanged-code flakiness. The acceptance document records these limits explicitly. I have not launched vendor clients or rerun the suite during this read-only review.

**Scope of the conclusion.** There is no new requirement here to defend against malicious trusted same-user tools, no recommendation for a process registry or lifetime token broker, and no claim that the screenshot failure has been repaired. The remaining approval question about broader vendor file access belongs to issue #16. No further architecture cut is necessary to satisfy issue #18 based on the source inspected in this pass.

Only this report was written by the auditor. Runtime code, settings, credentials and services were not changed.
