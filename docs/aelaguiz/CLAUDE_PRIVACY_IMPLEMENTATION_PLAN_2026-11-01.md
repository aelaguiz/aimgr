## 2. Scope and workflow contract

**Routing remains optional per account.** Extend the existing protected-account path with file/device/identity controls and retain its telemetry opt-outs. Do not infer an all-account Claude telemetry or sandbox change from the separate Codex decision. Ordinary accounts retain their route, environment and absence of proxy/CDP/route-helper dependencies. Existing per-account credential/config separation remains. Exact-build admission applies to **every** AIM-managed Claude execution, including ordinary accounts. Remote control and remote feature flags are disabled in **every** AIM-launched Claude session, including ordinary accounts, using launch-scoped settings; do not silently install machine-wide policy affecting unrelated launches. A protected account with missing protection never becomes ordinary.

Preserve commands, native Mac/Linux execution, live project edits and paths, model/effort/permission mode, basic terminal operation, personal/project skills, stdio and HTTP MCP including OAuth/resources/package dependencies, same-account and different-account concurrency, memory/instructions, history/resume/fork, subagents, account handoffs, AIM routines, supported in-session scheduled tasks, background work and maintenance/status. Include existing trusted nested AIM HTTP and native dispatch to the same or another account. Keep AIM-owned `SessionStart`, `UserPromptSubmit`, `Stop` and `StopFailure` hooks. No new daily flags, shell exports, project copies or per-command approval prompts. Preserve behavior that works in the paired baseline; do not certify unfinished unrelated restoration features as existing behavior.

Optional personal hooks/plugins, terminal extras, realtime/voice and GUI/extra integrations are not preservation requirements. Remove or suppress only their unnecessary automatic activation/collection; do not delete user configuration or disable infrastructure needed by required skills/MCP. Do not transfer the Codex shared-daemon prohibition into a blanket Claude background-process ban.

**Two narrow workflow limits explicitly accepted during implementation:** (1) custom provider HTTP headers are fixed to the admitted initial value for each session; edits to `ANTHROPIC_CUSTOM_HEADERS` take effect in a new session, while unrelated settings remain live; (2) a protected session may require a new session to access an extra folder outside its initial grants. Include that folder at startup, including through the existing `--add-dir` option. This does not permit removing ordinary project edits, freezing other settings, imposing a session cap, or changing skills/MCP/scheduling behavior. Startup extra-folder access is verified on both platforms; retain it as a regression test. This also covers a new external import outside the initially admitted roots: start a new session with that access included. Live edits and atomic replacement at admitted paths remain required; a new folder is not granted silently.

The implementation must not add a VM development workflow, new browser, Chrome firewall, hostile-browser bypass project, general DLP, credential broker, TLS interception, custom production CA, request rewriting, vendor fork/re-signing, machine-wide VPN, automatic failover, remote approval service or distributed process registry. Reuse existing routes, leases, locks and supervision. A new dependency must implement a named target and pass the retained-workflow tests; convenience is not sufficient justification. Ordinary-account admission must remain local and need no privileged proxy installation; install its approved artifact set without requiring a proxy profile.

**Completion requires evidence for each required target.** An unresolved read is not proof of upload, and a missing raw canary in one request is not proof of no transformed identifier. Record residual automatic metadata explicitly. The user explicitly accepted broad OS family and CPU architecture after seeing the actual Mac request fields. Hostname, exact OS version, hardware identifiers, terminal fingerprinting or an opaque derived device token remain protected. Necessary account IDs, per-account functional IDs, protocol/client version and accepted task content are distinguished from host fingerprint data. If a required protection cannot coexist with retained behavior, report the concrete conflict and keep that acceptance item open. Do not silently weaken protection or remove the feature.

### 4.2 Admit the complete approved artifact before any vendor code runs

Use a small local approval manifest and administrator-owned, content-addressed artifact directories, proposed at `/opt/aimgr-claude-runtime/artifacts/<package-digest>/`. Keep policy bundles and the active selector in the same protected installation. The Claude user/updater has read/execute access, no write access to artifacts, ancestors, approval records or policy. The installer alone stages and atomically activates a complete bundle. Reuse installation privileges; no new service runs to approve sessions.

An approval entry records display version, platform/architecture, exact package and executable/helper/resource hashes, compatible policy digest and AIM revision, review evidence, human approver and approval reference. Validate schemas, path containment, symlink targets, ownership/write permissions and all vendor-loaded code. Do not hash unrelated system libraries, compilers or independent MCP executables into Claude's version approval. Required vendor packages/helpers are included, even when they support skills/MCP.

The approval process records official provenance and the exact reviewed inventory. The installer accepts that explicitly approved bundle, verifies its complete inventory and integrity without running Claude, copies bytes into a protected staging directory and atomically renames the complete set into its digest path. It cannot grant approval or download a replacement. Read the atomically published active selector once, admit that immutable set and execute its exact target. Installation holds its own exclusive lock and retains all previous bundles; launch does not need a shared installation lock because no admitted directory is replaced or removed. Never resolve PATH again in the supervisor. Hold package availability through exec; retain old approved bundles while their processes run. Check and test both file replacement and parent-directory/selector replacement. Root deliberately tampering remains excluded.

All AIM paths use this admission, including ordinary accounts, `--version`, help, diagnostics, auth, maintenance, resume, schedules and background work. AIM status reports selected/approved/running identities from trusted records without executing an unknown vendor. Unknown/missing/corrupt approval, a changed helper, wrong platform or incompatible policy refuses execution locally. No online approval dependency is added; existing eligible offline-cache behavior survives.

**Ordinary accounts also need execution enforcement.** Use the bundled platform entry points, `native/claude/approved_launch_macos.c` and `native/claude/approved_launch_linux.c`, after artifact validation on every native launch. The Mac entry is unprivileged. The fixed Linux entry is administrator-owned/setuid solely to install AppArmor and the syscall filter; it drops all root IDs before executing the admitted vendor or isolated validator. Its common version-only policy protects approved code and excludes vendor update/install/cache execution locations; it does not restrict ordinary account data, metadata or networking. The protected-account path composes additional route/file/device policy around this same entry point. The current ordinary branch that directly executes Claude must therefore change, even though it still needs no proxy profile, CDP binding or native route helper. Installer delivery of this common component is part of the approved version-lock change.

The Linux candidate uses the fixed AppArmor entry described in section 4.4 for common execution/settings restrictions; the Mac candidate uses a minimal Seatbelt exec/write policy. Landlock is retained only inside the disposable Linux settings validator. Section 4.1 must establish the exact supported primitive, rule set and OS prerequisites before integration. The proof must cover vendor executables and loaded vendor code while allowing native builds, independent MCP programs and project executables. Denying a default updater directory is insufficient if the observed updater can activate from another location. Test alternative temp/cache/install locations, environment/settings overrides and shell/interpreter launches. If the platform cannot enforce the reviewed vendor's update paths without restricting retained tools, the common gate is unresolved for that platform, including ordinary accounts. Do not fall back to flags-only enforcement, a post-start monitor or a route helper required by ordinary accounts.

Expose one operator-facing read-only command, proposed as `aim claude privacy status`, reporting selected/approved/running artifact identities, applicable policy, account mode and the reason for refusal. It does not contact Anthropic or run Claude. Stage/activate through the existing installer with an explicit approved-manifest input; no self-approval CLI or automatic approval from a successful test. The ordinary `aim claude run`/resume/routine commands stay unchanged. Export the status as JSON for tests without secrets or personal identifiers. Unknown PATH-selected artifacts are reported and refused; do not silently substitute a different approved build when an explicit selection changes.

For each reviewed release, set supported update-disable controls before startup and verify them against automatic and explicit update/install entry points. Current official documentation describes `DISABLE_AUTOUPDATER` and the stricter `DISABLE_UPDATES`; their behavior must be tested on the exact candidate. Do not enable the broad nonessential-traffic switch merely to stop updates. [Official environment controls](https://code.claude.com/docs/en/env-vars)

Prevent vendor execution/loading from mutable update/cache locations in the native policy. Enumerate every retained vendor self-spawn/helper target and bind it to the approved artifact set. An ordinary tool is not classified as a vendor helper simply because Claude launches it; equally, calling vendor code through a shell/interpreter does not exempt it. Test the observed vendor updater paths through those interpreters. Arbitrary malicious tool attempts to run another client are outside scope, as are deliberate direct launches outside AIM. Admission cannot rely on killing an unknown child after it starts.

### 4.3 Keep private identity separate and preserve shared task state

Retain existing account paths and `HOME` semantics unless a measured incompatibility requires discussion. Add an AIM-owned identity/migration sidecar beside the account config, recording schema, underlying account UUID from existing credential identity, migration state and the audited identity fields. The label remains the existing directory locator; underlying identity binds its contents to the correct account. Different labels for the same underlying account need no new deduplication service; reusing a label for another account must not reuse its identifiers. Concurrent sessions sharing one config use its same stable private state. Unknown underlying identity refuses migration rather than treating a display email or label as authoritative.

Fresh login is a distinct state: its account UUID is not known until authentication completes. Keep the existing isolated login-staging directory, generate fresh temporary installation identity there, and use the selected account's validated route/original browser. Never seed staging from a reused label's app state or the personal home. After authentication, verify the expected account and bind/publish through existing credential identity/CAS checks. For reauthentication of the same account, retain its established private identity on activation; wrong-account completion must not overwrite either account's credentials or identity. Interrupted staging never becomes active state. Test initial login, same-account relogin, unexpected account, expired auth and restart between credential projection and sidecar commit. The native command remains version-approved before auth starts.

Classify `.claude.json` field by field. `userID` is private and demonstrably transmitted; classify `machineID` and every newly discovered persistent/cache identifier before sharing. Keep OAuth projection, project trust, MCP declarations, history, shared memories and instructions in their existing ownership/layout. Do not clone a complete home or merge an old identity back through auth publication, background synchronization or machine handoff.

Migration runs once with affected account owners stopped under the existing account/assignment coordination, before accepting new launches. Snapshot only files it changes, with private permissions. Build replacement state in a sibling staging directory, preserve unknown non-identity fields, validate required credentials/MCP access, and commit atomically with a migration marker. A crash before commit leaves the original state usable; a restart after commit detects completion and does not regenerate IDs. Rollback restores the snapshot only while owners are stopped and does not permit cross-account identity reuse. No silent deletion of credentials/history, reauthentication or per-launch ID regeneration.

For an ID known to be copied across accounts or across the normal personal home, create fresh account-private identity using the pinned client's established format/generation behavior under an isolated first-start lock. Do not derive it from hostname, hardware UUID or home path. Keep already unique account-private IDs unless the inventory finds another reason to change them. Migration cannot erase links already sent to Anthropic; it prevents future reuse. Keep this state local: the same account may have a different private installation ID on another machine. Existing credential handoff must not import a source machine's global identity or another account's app state. No new Redis identity-sync service or cross-machine identity replication is required. Test first-start concurrency, label rename/reuse, refresh, offline cache and handoff explicitly.

Use the existing Mac credential adapter and native credential storage. Test synthetic keychain/MCP credentials and refresh; do not introduce a replacement credential store. Unneeded global state becomes inaccessible to Claude; required third-party auth remains available through its current mechanism. If a required token contains machine-specific attestation or cannot migrate transparently, retain it as an unresolved target rather than silently dropping MCP.

### 4.4 Apply the file/device boundary before Claude starts

Compose launch in this order: resolve account/classification; admit the complete package; resolve its policy; prepare classified state and required settings; validate account/route binding; enter the existing enforced route for protected accounts; apply file/device/exec restrictions after privilege drop; close unintended inherited handles; execute the approved supervisor/vendor target. No provider code runs during earlier validation. A prepared-launch object is not authorization to bypass the final checks. Direct AIM HTTP calls retain their existing protected transports.

**Linux:** use the tested fixed native entry with enforcing AppArmor profiles and a narrow `uname` seccomp listener. The original mount-view candidate is superseded: a process-wide mount restriction and blanket no-new-privileges interfered with trusted nested AIM/tool workflows. Each approved vendor image enters its account-specific file policy; ordinary tools retain normal host access, and executing the approved vendor again restores its restrictions. A fixed immutable launcher is the only unconfined reentry target, and it applies the new policy before executing its fixed sibling vendor. Keep existing cgroup/network enforcement outside this layer. Preserve absolute paths, writable projects, toolchains, required skills/MCP and native tool privileges.

The administrator-installed Linux entry has one fixed protocol and needs setuid only to install AppArmor and the syscall filter. It accepts canonical data paths and fixed modes, never profile text, an arbitrary executable or a privileged shell command. Require global AppArmor enforcement and verify the exact effective profile after entry. Escape all rule-language metacharacters. Admit the exact selected launcher with setuid required; reject privileged mode bits on every other artifact and reject executable file capabilities. Drop real, effective and saved UID/GID before any vendor code, preserve the caller's actual supplementary groups, restore the private environment only after policy entry, and close unintended descriptors. Ordinary mode applies common settings/update restrictions while retaining ordinary file and device access; it does not require a proxy route installation.

Only protected vendor tasks lose automatic exact-kernel `uname` access. The unprivileged listener classifies the actual kernel AppArmor label, refuses unreadable labels, and allows ordinary/tool calls. It retains no root identity or public request API. Nested entries reuse a proven inherited filter; the listener ends only when the kernel reports that all inheriting tasks have gone away, including background descendants. Do not introduce a root daemon merely for cleanup. Named AppArmor profiles persist independently of processes: safe reclamation and measured resident cost remain an integration gate. Never unload a profile still used by a task, infer safety from one process scan, or impose an unapproved session cap. Candidate staging leaves running approved sessions intact.

**macOS:** use a small native policy applied before the vendor's first instruction. Compose file restrictions with exact admitted-image-path metadata restrictions demonstrated in the experiments. The vendor binary remains unchanged and retains its original signature. Cover every reviewed vendor helper, not just the main binary. Preserve ordinary tools' necessary OS discovery under the accepted tool-risk boundary. Selected sysctl/IOKit/version-file/`sw_vers` and UUID-syscall paths require paired probes; `gethostuuid` must not remain an unnoticed alternative. Foundation hostname and hardware/Mach paths remain explicit tests. Do not use the broad host-information denial that killed clients in research. Custom policy compatibility is tested for each supported OS/build combination; an unknown combination is refused for protected launches, not silently run without policy.

The access list is generated from existing cwd, worktrees/git common directories, configured additional directories, instruction/memory sources, resolved skills/MCP packages and actual toolchain/auth dependencies. Resolve symlinks and allow the real required target without exposing its entire home ancestor. Test relative config semantics, atomic native writes, package updates by existing independent tooling, and already-trusted workspaces. Changing cwd or operating on another legitimate configured project within the admitted roots must work without new approval prompts. The user accepted starting a new session to add a folder outside those roots; startup `--add-dir` must preserve native access. Other filesystem restrictions that block retained workflows remain failed compatibility gates.

The trusted AIM preparation code may read the shared settings it already owns, then project only required fields. Claude does not receive an unrestricted copy of unrelated home state. Close all inherited descriptors except required stdio, the identified AIM control channel and documented tool descriptors. Preserve the Mac identity helper's existing closure of its environment-transfer descriptor and test the complete chain; close other unintended inherited descriptors at the final launch boundary. Retain real IPC, PTY, pause/resume and Ctrl-C behavior. Never put raw environment or credentials in argv or logs.

Inventory inherited environment separately: remove only unrelated secrets and automatic terminal/device detector inputs proved unnecessary; preserve required build/MCP variables and basic terminal capability/locale. A blanket environment wipe is prohibited. If an environment variable is simultaneously required by native tools and readable by the vendor, record that concrete conflict. Do not solve it by a new secret broker or silently exposing it. Identifying data returned by an intentionally invoked legitimate tool remains accepted task output.

Retain protected-account `DISABLE_TELEMETRY=1` and `DISABLE_ERROR_REPORTING=1`. Pin `DISABLE_GROWTHBOOK=1` for **all** AIM Claude accounts, including ordinary accounts, to prevent remote or cached feature flags from changing managed-settings eligibility. The user explicitly approved this scope on 2026-11-01 and accepted loss of experimental features. Skills, MCP, concurrency and scheduled jobs remain required and must pass with this pin. These must be fixed in the composed launch settings as well as the initial environment: setting environment variables only in `nativeProxyEnvironment` is insufficient if native settings override or reload them. Apply the same rule to update-disable variables for all AIM sessions. Inventory optional automatic diagnostics, feedback uploads, terminal-related background requests and provider-directed collectors. Disable the unwanted paths individually where supported. Preserve independent user-owned OpenTelemetry destinations. Ordinary account telemetry remains unchanged by this plan.

Compose an immutable launch overlay containing only AIM-owned privacy keys plus the existing required overlays, preserving unrelated settings and live edits. Pin the initially effective harmless `ANTHROPIC_CUSTOM_HEADERS` string, including an explicitly empty value, for every session; the user accepted applying later custom-header edits only in new sessions. Verify the exact build's precedence against user, project, local, managed, forwarded `--settings` and environment-bearing settings. Test empty/unset values as well as false-like values; their meanings differ by key. A source with higher precedence that would undo protection must cause admission refusal, and live reload must leave protected values effective or be prevented from reaching the vendor before it can collect/send. A post-send watcher is not enforcement. If the native client cannot maintain these scoped overrides while preserving required live settings, the section 4.1 settings gate remains open. Do not freeze all settings or remove live shared edits to claim success. The native exec boundary must still prevent unapproved update activation even when an update-disable variable is removed. [Official settings environment precedence](https://code.claude.com/docs/en/env-vars#precedence)

The exact build treats repeated `--settings` flags as last-wins and snapshots the selected file at startup. Compose that selected source with required AIM hooks and critical values into one snapshot; normal user/project/local settings remain live. Preserve source-directory semantics: file input uses the native-resolved target directory, while CLI inline JSON uses `claude-<uid>` beneath the original `CLAUDE_CODE_TMPDIR` or native temporary directory. An immediate sibling snapshot avoids rewriting permission globs, sandbox paths and hook trust. Do not relocate it into a nested scratch directory or derive its origin from the validator's cleaned environment. Exact-filename reach grants, hardlinked sources and unwritable source directories still require compatibility proof. Accept representative native-valid settings between 1 and 2 MiB, and bound the exact compact composed bytes to the native 2 MiB limit. Required controls consume part of that allowance. If an already near-limit source overflows after composition, refuse clearly before launch; increasing the native limit or adding another settings transport is outside scope. Both platforms have passed the 1.5 MiB native handoff/validation cases. Validate the complete composed object before giving a session credentials or network access: native schema rejection of an unrelated field can discard the privacy values too. ## 5. Visible failures and recovery
