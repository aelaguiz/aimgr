# Decision needed: enforce local privacy rules inside Codex

**This is a proposed change to the accepted design, not an authorized implementation.** The accepted plan requires official, unmodified Codex. Source review of both its pinned build and official 0.166.0 found that cloud requirements can replace local feedback, update-check, remote-control and explicit telemetry-export settings, including after a session starts. The [cold review](CODEX_PRIVACY_M1_COLD_REVIEW_2026-11-04.md) records exact source evidence. Existing directory isolation, environment-local authentication and the analytics opt-out do not fix this separate policy conflict.

This establishes that capabilities can be re-enabled; it is not evidence that private data was uploaded in these tests. Feedback upload is explicitly invoked, and the current remote-control environment marker suppresses saved-state startup but is not a permanent prohibition against a later enable request. The required guarantee is that the named local privacy rules cannot be loosened remotely.

The practical choices are:

1. **Allow design of targeted Codex changes, then cold-review that revised design before implementation.** Local administrator privacy requirements must remain authoritative at initial load and every reload. Provider telemetry must be rejected at the native effective-exporter boundary while independently owned collectors retain their ordinary configuration and edits. Preserving the requested account support and workflows is a design and test requirement, not an established result. This approach requires maintaining and testing a patched Codex build when upstream changes. It changes the official-unmodified-artifact requirement and macOS build/signature provenance. No source patch or replacement package has been produced under the current authorization.
2. **Keep the official-unmodified requirement.** Preserve the completed work and leave milestone 1 unaccepted until a verified official capability provides these guarantees. Official 0.166.0 is not that capability. An account-plan snapshot, readonly cache or startup preflight cannot substitute for a session-lifetime rule.

The recommended next design, if choice 1 is authorized, has a strict boundary:

- Keep native cloud loading and unrelated organization controls. Add only a local administrator privacy ceiling for the named controls; a remote refresh cannot loosen it. Preserve the existing protected primary-auth fields.
- Perform exporter decisions after native trust, layer precedence and profile selection, before constructing any exporter. Preserve independent collector endpoints, headers and content choices. Cover all native export owners and reload paths; verify redirect behavior instead of assuming destination checks cover it. The provider-recipient inventory remains tied to the reviewed release and observed request owners.
- Keep ordinary shell tools, SDK credentials, Chrome, SSH, local integrations, subagents and nested AIM behavior. No new proxy dependency in milestone 1, no HTTP interception, no injected library, and no persistent settings/policy service.
- Do not use permission to patch the client as permission to redesign settings origins, shared storage or the scheduler. Any proposed subtraction from the existing adapter must independently show equivalent behavior and a smaller maintenance surface.
- Record the exact upstream commit, patch, build toolchain, complete package hashes and macOS signature provenance. Builds and tests remain on isolated remote machines; native acceptance uses synthetic or already authorized sacrificial identities only. Normal-use approval remains separate.

Required tests for that changed capability would add conflicting cloud requirements at startup and during live refresh; personal-to-managed account transitions; conflicts from every local/managed layer; saved remote-control state and explicit enable requests; independent collector edits; provider endpoints across all three telemetry signals; and refusal before prohibited optional telemetry, feedback or remote-control side effects when policy cannot be established. Required model/cloud-policy traffic and independent collectors remain separate. Existing M1 acceptance remains required, including ordinary-tool compatibility. A cold reviewer must review both the revised design and the final implementation for overbuild and plan compliance.

A cold reviewer checked this decision proposal against exact official 0.166.0 source, found no missed supported stock alternative, and agreed its scope is sufficient for approval to revise the design. That review does not approve implementation or promise patch feasibility. The distinctions about explicit feedback, remote-control startup and prohibited side effects above incorporate the review's corrections.

Neither choice permits claiming the current implementation complete. SQLite initialization, MCP maintenance conversion, named permission roots, platform coverage and the final full test/review pass also remain unfinished. Milestone 2 stays behind the original milestone-1 readiness gate.
