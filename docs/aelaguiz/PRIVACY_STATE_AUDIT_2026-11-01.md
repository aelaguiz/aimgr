# Claude and Codex persistent-identifier audit

**Separate application homes isolate the model-request IDs we tested, but they do not isolate every identifier the clients can read and send.** The offsite Linux and rented-Mac experiments confirmed a second Codex identifier path outside `CODEX_HOME`. The [Codex privacy plan](CODEX_PRIVACY_PROXY_PLAN_2026-11-01.md) now includes disk, database, keychain and process identity ownership, explicit remote-control disablement, and tests for both.

These are observations of official Codex `0.163.0-alpha.5` and Claude Code `2.1.316` using synthetic credentials and local test servers on 2026-11-01. No personal account, personal home, existing browser profile or physical Mac was used as a test fixture. The results establish client behavior on these paths; they do not establish how a provider uses a field after receiving it.

1. **Both clients send a persistent ID with ordinary model requests, even with telemetry disabled.** Codex read `CODEX_HOME/installation_id` and sent it in `client_metadata["x-codex-installation-id"]`. Claude read the config-directory `.claude.json` `userID` and sent it as `device_id` inside the JSON-encoded `metadata.user_id` field. The captured device ID matched the on-disk value in every selected model experiment. The experiment covered API-key `codex exec` and `claude -p`, not subscription-auth daemon reuse.
2. **Fresh homes separated those IDs; copying a home preserved them.** Each client completed five cases on each platform: fresh A, restart A, fresh B under the same OS home, a copy of A, and a fresh application home under a different OS home. A and its restart/copy shared an ID; each fresh application home had a different ID. All 20 executions completed a synthetic model exchange. A migration therefore needs a deliberate list of shared settings/history and private identity files. Copying or linking an entire existing home is insufficient. [Linux evidence](evidence/privacy-state-2026-11-01/linux-identity.json), [Mac evidence](evidence/privacy-state-2026-11-01/macos-identity.json).
3. **On macOS, `codex doctor` sent a desktop installation ID from outside its application home.** With a synthetic installed-app bundle and backend appcast enabled, it read `~/Library/Application Support/com.openai.codex/production-appcast-bootstrap.json`. Its update-check request included that file's `installation_id`, architecture, app version and OS version. We held `CODEX_HOME` constant and changed only the synthetic OS home and desktop canary: the outgoing ID changed from canary A to canary B. Telemetry remained off. Both HTTPS requests terminated at a loopback capture server with certificate verification enabled. This path needs its own treatment; the plan does not claim a separate Codex home solves it. [Captured requests](evidence/privacy-state-2026-11-01/macos-doctor.json).
4. **Claude opened Linux's `/etc/machine-id`.** Its raw value did not appear in the captured model requests. Claude also created a separate config `machineID`, which differed from the OS value and likewise did not appear raw in those requests. The evidence does not exclude a transformation, another request path or later use. The file-access inventory keeps this as an unresolved global read, rather than calling it proven upload or declaring it harmless. [Filesystem observations](evidence/privacy-state-2026-11-01/filesystem-observations.json).
5. **Codex transmitted the supplied terminal name/version and the test host's OS/architecture.** The synthetic terminal marker appeared in the model WebSocket User-Agent on Linux and macOS despite telemetry opt-out. The Mac value was `codex_exec/0.163.0-alpha.5 (Mac OS 15.8.0; arm64) PrivacyAuditTerminal/AUDIT_VERSION_123 (codex_exec; 0.163.0-alpha.5)`. Separate homes do not remove those fields. The wrapper's terminal-version reduction still needs compatibility tests; no supported replacement of the functional OS metadata has been established.

The supported remote-control settings are now explicit in the plan:

| Client | Enforced setting | What the offsite probe established |
| --- | --- | --- |
| Codex | `/etc/codex/requirements.toml`: `allow_remote_control = false` | Seven RPCs refused before and after app-server restart on both platforms. |
| Claude | Managed settings: `disableRemoteControl: true` | Standalone remote-control command refused on both platforms despite user-level `false`. |

For Codex, all 28 RPC calls returned code `-32600` with `remote control is disabled by managed requirements`. Effective requirements reported `allowRemoteControl: false` in each of the four app-server processes, and local `config/read` still succeeded. This covers fresh/restarted stdio app-server processes. It does not prove an already enrolled relay stops without restarting its owner. [Linux policy results](evidence/privacy-state-2026-11-01/linux-remote-control.json), [Mac policy results](evidence/privacy-state-2026-11-01/macos-remote-control.json).

For Claude, both standalone commands exited with the exact managed-policy error. The additional `--remote-control -p` probe timed out and did not establish interactive flag/toggle behavior; its evidence is intentionally marked unsuccessful. Normal model turns passed under the installed managed setting. The [official setting reference](https://code.claude.com/docs/en/settings-reference#disableremotecontrol) documents enforcement for the command, flag, auto-start and in-session toggle; those other lifecycle paths still need their dedicated fixtures. [Linux Claude results](evidence/privacy-state-2026-11-01/linux-claude-control.json), [Mac Claude results](evidence/privacy-state-2026-11-01/macos-claude-control.json).

The current plan preserves simultaneous sessions, scheduled work, required skills/MCP, native tools and history. Later R15 selects standalone Codex and excludes the shared daemon; R16 waives terminal extras, realtime/voice and optional GUI/hooks/plugins except required package dependencies and AIM-owned scheduling hooks. Remote-control prohibition remains independent of those later decisions. Existing owners must be quiesced during the scheduled transition because Codex reads its remote-control requirement at startup. Optional telemetry controls remain separate from that requirement.

The source inventory also identifies state that a home migration must handle deliberately:

| State | Lookup or ownership | Required treatment |
| --- | --- | --- |
| Primary Codex auth | `auth.json`; `Codex Auth` keychain entries derive from canonical home | Keep account-private; preserve supported auth migration. |
| Encrypted secrets | `secrets/{codex_auth,mcp_oauth,gateway_oauth,local}.age`; separate home-derived key association | Preserve decryptability; do not link ciphertext blindly. |
| MCP OAuth | Ordinary `Codex MCP Credentials` key derives from server identity, not `CODEX_HOME` | Preserve third-party credentials; test its separate storage contract. |
| Saved relay enrollment | Shared SQLite `remote_control_enrollments` | Enforce relay prohibition without deleting shared history. |
| Config and app caches | Cloud/managed config, model caches and app-directory caches | Classify account-bearing entries before sharing. |
| Thread, queue and memory state | Existing shared history/database | Preserve accepted task continuity and account-rotation rules. |
| Process cookies and cached IDs | Request-owning process | Keep account owners separate; a fresh directory does not reset a reused process. |
| External-client attestation | Opaque token supplied by an attestation-capable app-server client | Inventory the supplier; do not assume native CLI generates hardware attestation. |

These entries are source findings, not runtime-tested secret migrations. The pinned source is [Codex commit 54201ea](https://github.com/openai/codex/tree/54201ea65a3501d09a87c776376a0c16aa39db70); it is distinct from the tested official binary version. Relevant owners are [primary auth storage](https://github.com/openai/codex/blob/54201ea65a3501d09a87c776376a0c16aa39db70/codex-rs/login/src/auth/storage.rs), [local secret keys](https://github.com/openai/codex/blob/54201ea65a3501d09a87c776376a0c16aa39db70/codex-rs/secrets/src/local.rs), [MCP OAuth storage](https://github.com/openai/codex/blob/54201ea65a3501d09a87c776376a0c16aa39db70/codex-rs/rmcp-client/src/oauth.rs), [relay persistence](https://github.com/openai/codex/blob/54201ea65a3501d09a87c776376a0c16aa39db70/codex-rs/state/src/runtime/remote_control.rs), [in-memory cookies](https://github.com/openai/codex/blob/54201ea65a3501d09a87c776376a0c16aa39db70/codex-rs/http-client/src/chatgpt_cloudflare_cookies.rs), and [attestation forwarding](https://github.com/openai/codex/blob/54201ea65a3501d09a87c776376a0c16aa39db70/codex-rs/app-server/src/attestation.rs).

The Mac file trace also showed OS-version and certificate/keychain-path access. Certificate-store access alone is not evidence of credential collection. `fs_usage` does not expose all keychain service activity, IOKit calls, memory-only state or unexecuted branches. Linux `strace` followed file, network and child-process syscalls; neither trace is a proof that every dependency and future execution path has been observed.

**At the end of this initial audit, implementation had three concrete design problems:** preserving arbitrary relative configuration paths under new homes, migrating classified identity/secrets without losing access, and preventing the macOS diagnostic path from reusing personal desktop identity. The plan does not authorize deleting credentials/history, rewriting desktop identity, disabling diagnostics or changing daily `HOME` semantics. The later version-lock requirement explicitly supersedes normal automatic updates: only reviewed, explicitly approved artifacts may execute. That initial review required saved-enabled relay, synthetic ChatGPT-auth daemon reuse, keychain/encrypted-secret and telemetry-positive-control coverage. The later standalone decision replaces shared-daemon reuse with refusal/absence tests and actual retained-backend coverage; the other relevant cases remain pending.

Reproduction uses the [identity probe](../../scripts/privacy-state-audit.py), [Codex policy probe](../../scripts/privacy-remote-control-audit.py), [Claude policy probe](../../scripts/privacy-claude-control-audit.py) and [macOS diagnostic probe](../../scripts/privacy-macos-doctor-audit.py). Each refuses a reused fixture directory and requires the offsite audit marker. These guards identify the intended test environment; the independent network boundary must already be installed by the operator. Linux ran unprivileged in a network namespace containing only loopback. The rented Mac allowed no outbound provider/web connection; its external network rules permitted only the pre-existing narrow SSH routes. The local TLS proxy used for the doctor canaries never forwards a request and never installs a trust certificate into a system store.

The selected evidence comprises 10 Linux and 10 Mac model executions, 28 remote-control RPC refusals, four effective-policy readbacks and two synthetic macOS desktop-ID captures. The initial Linux discovery runs are not counted again. The first doctor capture used an unsuitable certificate and was rejected by the client; after correcting the fixture to use a proper CA-signed leaf, both canary captures passed. `doctor` itself reported diagnostic failures because the fixture has no real account, has an intentionally incomplete app bundle and returns mock HTTP errors. Its nonzero exit is retained in the evidence; the experiment's assertion is the captured canary request, not a clean doctor report.

The [binary manifest](evidence/privacy-state-2026-11-01/binaries.json) records exact versions and SHA-256 hashes. New package archives were verified against official registry integrity metadata; the Linux Claude binary came from the existing test installation and is labeled accordingly. Raw traces and synthetic request captures remain in the offsite audit archive. Public evidence contains no account credentials, real installation identifiers, cloud resource identities, proxy exits or personal browser data. No real-account login or human-verification challenge occurred.

The independent cold reviewer read all nine public evidence files, checked all four scripts against their claims and signed off on this bounded audit and the R12/R13 expansion. They found no new material issue or unapproved workflow removal. They explicitly withheld full product-plan approval for the three design problems and broader lifecycle tests described here.

Cleanup of the original identity-audit rental: the raw Mac evidence is archived on the offsite Linux VM. AWS now confirms that the audit instance is terminated; its dedicated host is undergoing the AWS scrub before reuse. The exact-instance termination failsafe remains enabled. The task-specific SSH private key, AWS key pair and temporary GCP access rule were removed. The existing dedicated-host release schedule remains unchanged; this audit allocated no additional dedicated host.

## Follow-up: native isolation mechanisms

The later [Mac/Linux isolation investigation](PRIVACY_SANDBOX_FEASIBILITY_2026-11-01.md) now includes actual native tool calls and request captures. It demonstrates exact OS-version suppression, explicit hardware-UUID syscall denial and a bounded successful denial of the Codex desktop bootstrap ID while retaining its CDN fallback. It also records policy-induced startup failures, residual host information and shared-config path failures. Those later results refine the mitigation options; they do not change this audit's original captured-ID findings or certify the full product plan.

**Later scope and version decisions:** this historical audit does not authorize running its tested versions under the expanded design. See the [current canonical requirements and shared upgrade gate](CODEX_PRIVACY_PROXY_PLAN_2026-11-01.md#9-privacy-review-after-a-claude-or-codex-upgrade); candidate review execution and normal-use approval are distinct.
