# Isolating Claude and Codex while keeping the Mac workflow

2026-11-01. Investigation under the [Codex privacy plan](CODEX_PRIVACY_PROXY_PLAN_2026-11-01.md), covering both official CLI binaries. **Native Mac restrictions can hide the identified OS-version fields and selected persistent/device identifiers while retaining actual native tool execution. The tests do not justify abandoning the Mac development environment.** The rented Mac experiments now demonstrate this with unmodified Claude 2.1.316 and Codex 0.163.0-alpha.5. They also establish that a blanket host-information block is incompatible with both clients: one broader hardware-information denial kills them at startup.

**Recommendation:** continue with narrowly scoped native controls and account-private identity state. Keep the current terminal, editor, project paths, Mac tools and original Chrome instances. Do not select a VM or deploy the experimental blanket policy. The complete zero-workflow-change product remains unproved: basic terminal use, relative settings and required-secret migration still need compatible designs/tests; complete standalone lifecycle, required package/secret migration, full AIM schedules and exact-build admission remain to be accepted. These are explicit unresolved requirements, not accepted reductions.

The priority is the user's latest instruction: “how can we do it with as little impact to my workflows as possible.” Considering a VM is permission to investigate it, not acceptance of a different execution host, fewer sessions, missing tools, copied settings, or a new daily workflow. No product launcher, account, browser, or physical Mac configuration was changed in this investigation.

**Scope updated after these experiments:** the [current plan’s R1/R15/R16](CODEX_PRIVACY_PROXY_PLAN_2026-11-01.md#1-requirements-assumptions-and-exclusions) now requires explicit approval of exact Claude/Codex builds and avoids Codex’s shared daemon. Terminal extras, realtime/voice, optional user hooks/plugins and GUI/extra integrations are not preservation requirements. Skills/MCP, required packaging/auth, AIM scheduling hooks, basic terminal/native tools, history, concurrency and original Chrome remain. The bounded experiments below are historical findings; none grants normal-use build approval; the later standalone workflow results are recorded immediately below. Owner-exit behavior, relative settings and required-secret migration still need proof.

**Standalone follow-up:** the [offsite workflow tests](PRIVACY_STANDALONE_TESTS_2026-11-01.md) now demonstrate concurrent Linux TUIs, project skills, stdio MCP and authenticated HTTP MCP tools, resources, subagents, resume/fork and OS-scheduled native AIM handoff without shared-daemon attachment. They found a native first-start SQLite migration race; finite native initialization before concurrent startup passed. The complete official package also needs `codex-code-mode-host`. These are concrete setup/package requirements, not permission to cap sessions. The rented Mac has now passed the same retained workflow and three-session concurrency under the selected metadata restrictions, with its captured OS version changing to Unknown. Abrupt-owner cleanup failed on Mac: the background heartbeat survived SIGKILL, and a separate failed-start sample found GitHub plugin-check children still alive. These are lifecycle gaps to close, not a reason to restore the shared daemon. Mac interval-triggered native handoff passed, while two baseline calendar triggers did not run on this rental; calendar scheduling is unverified. settings/secret migration and complete product enforcement remain open. The earlier native Mac mechanism evidence below is unchanged.

## 1. What the least disruptive design would look like

The intended experience is still `aim` in the same terminal and repository. No new per-command privacy prompt system is proposed; a required tool denied by the candidate is a compatibility failure to resolve or discuss. AI Manager establishes the boundary before starting the official client, keeps every retained request owner and descendant inside it, and supplies account-private provider state. Project edits remain visible immediately to the existing editor and other sessions. Native commands still execute on the Mac. The established per-account local Chrome CDP instances and manual sign-in remain unchanged.

This design has three separate responsibilities:

1. Keep provider identity, credentials and caches separate between accounts, while preserving legitimate same-account state and shared task history/settings.
2. Restrict the whole vendor process's reads of unrelated personal files and identifiers, including global locations outside its application home. Preserve access to the actual project, declared additional workspaces, toolchains, instructions, skills and required tool state.
3. Keep the existing external, fail-closed proxy enforcement and approved telemetry/remote-control policies. A filesystem sandbox does not replace the proxy or remove fields already inside HTTPS requests.

The boundary must begin before the first client instruction, not after startup. Starting a request-owning backend outside it and sandboxing only the shell children does not work. R15 removes the shared Codex daemon from the proposed runtime. Existing owners must stop during the already accepted transition. A new invocation must not attach to an older, unrestricted owner. A failed boundary must produce a clear refusal, without an unsandboxed retry.

The remaining uncertainty is concrete: **can the restrictions that hide host identifiers also preserve every required native tool and integration?** That requires paired tests. A blocked build, unavailable keychain credential, lost required skill/MCP or missing scheduled job is a failed candidate, not an accepted privacy improvement.

## 2. Options in order of workflow impact

| Candidate | What stays familiar | What it protects | Cost or unresolved conflict |
| --- | --- | --- | --- |
| Native client with private identity state and selective file/API denials | Current terminal, Mac tools, repository paths and execution host | Known disk identifiers, tested hardware-ID access paths and identified OS-version fields | Runtime-tested candidate. Unknown locations and allowed OS APIs remain reachable; terminal reduction needs basic-functionality tests; extras are now waived. This is targeted suppression, not a private OS. |
| Native client with an explicit filesystem read allowlist and selected OS restrictions | Same Mac tools and live worktrees, if compatible | Unrelated files, including newly introduced identifier files outside allowed roots | Tool configuration, keychains and IPC need compatibility work. Host OS/hardware may remain visible. Custom Mac policy needs ongoing regression testing. |
| Client in a guest, native Mac execution through an existing service | Potentially keeps native builds and project paths | Separates the provider-facing client's own OS/home | Codex remote execution rejects worktree/cwd workflows and limits detached-session retention. Native helper state also needs containment. No equivalent transparent Claude path was established. |
| Local Linux VM with explicitly shared worktrees | Same Mac desktop, editor and terminal entry point can remain | Separate guest filesystem, kernel and machine state | Commands execute on Linux. Native Mac builds, simulator/device integration, localhost and tool credentials need a different arrangement. This is an execution-host tradeoff. |
| Local macOS VM with explicitly shared worktrees | Retains macOS tooling inside a guest; host editor/terminal can remain | Separate guest OS/home and virtual machine identity | Tool installation, keychain/signing, devices, background services, resource usage and shared state need verification. It is not a zero-change substitute. |
| Offsite development machine | Mac remains a terminal/editor/browser frontend | Removes the personal machine from the native client environment | Connectivity, filesystem latency, local services and device workflows change. No evidence currently requires this larger move. |

A local VM does not require moving Chrome or replacing the Mac desktop. Apple supports both Linux and macOS guests and explicit directory sharing; macOS guests can use shared directories from macOS 13 onward. Preserving paths is possible in principle, but path preservation alone does not prove file watching, locking, socket behavior or settings compatibility. [Apple Virtualization](https://developer.apple.com/documentation/virtualization), [shared directory semantics](https://developer.apple.com/documentation/virtualization/shared-directories), [guest mount points](https://developer.apple.com/documentation/virtualization/vzvirtiofilesystemdeviceconfiguration).

One clean VM shared by every account can hide the personal host while giving those accounts a common guest machine identity. Separate account homes do not change that fact. Separate guests could separate more machine-level state but add memory, disk and service overhead. Neither topology is selected, and there is no proposal to create a VM per session or cap concurrency. Apple explicitly models a persistent virtual machine identifier; cloning initialized guest state can copy identifiers just as cloning an application home does. [Apple virtual hardware identity](https://developer.apple.com/documentation/virtualization/vzmacmachineidentifier), [installing a macOS guest](https://developer.apple.com/documentation/virtualization/installing-macos-on-a-virtual-machine).

## 3. Built-in tool sandboxing does not contain the vendor client

Claude documents that its Bash sandbox excludes the client, built-in file/web tools, hooks, MCP servers and other helpers. It also documents that full-process containment requires putting Claude itself inside an external boundary. Turning on `/sandbox` alone cannot prevent Claude's own startup or request code from reading identifiers. [Claude sandbox scope](https://code.claude.com/docs/en/sandboxing#what-runs-outside-the-sandbox).

Codex's source provides filesystem and process sandbox machinery, but its normal tool sandbox is not an independent boundary around all request-owning processes. The Mac base policy allows numerous host-information queries, including OS version, hostname, CPU, memory and hardware model. The source explicitly distinguishes its CPU policy from browser fingerprinting concerns. Those defaults should not be mistaken for the privacy policy requested here. [Pinned Codex Mac base policy](https://github.com/openai/codex/blob/54201ea65a3501d09a87c776376a0c16aa39db70/codex-rs/sandboxing/src/seatbelt_base_policy.sbpl), [policy construction](https://github.com/openai/codex/blob/54201ea65a3501d09a87c776376a0c16aa39db70/codex-rs/sandboxing/src/seatbelt.rs).

An external wrapper can apply OS restrictions before executing the unmodified binary. This preserves the vanilla-binary requirement. It must also cover native updates/replacements, detached owners, scheduled launches and reattachment. Merely inheriting `HOME`, a proxy variable or a tool permission setting is insufficient.

## 4. What the Linux experiment proved

The experiment ran on the existing offsite Ubuntu VM using the same official Codex `0.163.0-alpha.5` and Claude Code `2.1.316` binaries as the [state audit](PRIVACY_STATE_AUDIT_2026-11-01.md). The [binary manifest](evidence/privacy-state-2026-11-01/binaries.json) records their hashes. Each client and its children ran inside a restricted mount/PID/UTS/IPC view. The outer network namespace had only loopback; every model request terminated at the synthetic local server. No account or browser login was involved.

| Observation | Measured result | What it establishes |
| --- | --- | --- |
| Official model execution | All 10 cases completed: five per provider | These exact model paths work inside the external filesystem boundary. |
| Fresh/reused/cloned account state | Captured request IDs matched each case's application state | Sandboxing does not itself stop the client sending its own persistent ID. A cloned home still copies that identity. |
| Private file read | Denied inside; readable by the same Unix user outside | Denial came from the boundary, not a missing fixture or ordinary file ownership. |
| Symlink and shell child | Both failed to read the private file | These two indirect access paths did not reopen the hidden directory. |
| Shared project edit and Git | Edit immediately visible outside; Git initialization/status worked | Basic worktree operations can remain in place. |
| Terminal allocation | PTY creation succeeded | A required terminal primitive works; interactive terminal behavior is not yet certified. |
| Process and service visibility | Only sandbox PIDs; host home, `/run` and `/sys` absent | This filesystem/process view did not expose those host resources. |
| Hostname and machine-ID file | Fixture values visible | These particular namespace/file sources can be separated from the host. |
| Kernel and hardware context | Same kernel release; `/proc/cpuinfo` and `/proc/meminfo` readable | A Linux namespace is not a separate OS and this profile still exposes hardware context. |
| Functional metadata | Codex still sent OS, architecture and the synthetic terminal label/version | Filesystem containment does not strip functional request metadata. |
| Individual settings-file mount | Atomic replacement failed with `EBUSY` | Binding individual config/auth files is not a transparent settings/refresh design. |

The ten cases are fresh A, repeated A, fresh B, cloned A and a separate synthetic OS home for each provider. They are sequential API-key model fixtures. They do not certify ChatGPT subscription auth, daemon reuse, interactive TUI, simultaneous sessions, hooks/MCP, scheduled jobs, updates, or real-account functionality. The shell/Git/PTY probes were direct processes inside the same boundary, not model-selected tool calls. [Full sanitized results](evidence/privacy-sandbox-2026-11-01/linux.json), [reproduction script](../../scripts/privacy-sandbox-feasibility.py).

The initial fixture attempts found Ubuntu's enabled restriction on unprivileged user namespaces and a root-created mount-parent permission issue. The final research fixture used privileged mount setup, then dropped the payload to the synthetic user with no effective capabilities and `no_new_privs`. The host's AppArmor policy was not disabled. This proves the tested containment behavior, not a production privilege/installer design. Bubblewrap is a policy-building primitive whose guarantees depend on the caller's actual mounts, descriptors, namespaces and services. [Bubblewrap security scope](https://github.com/containers/bubblewrap#sandbox-security).

The follow-up exercised actual model-selected shell tools in both clients, with matched unsandboxed controls. Each client edited the shared synthetic project, initialized Git, allocated a PTY, compiled and ran a tiny C program, and returned the tool output to the mock model server. Both sandboxed cases passed. The first sandboxed build failed because Ubuntu's `/usr/bin/cc` points through `/etc/alternatives/cc`, which the synthetic `/etc` lacked. Adding only that compiler link into the synthetic filesystem fixed the build; the private-file and symlink denials still passed. This is evidence for those concrete native operations, not interactive terminal, daemon, scheduling or complete toolchain parity. [Baseline](evidence/privacy-sandbox-2026-11-01/linux-workflow-baseline.json), [initial compiler failure](evidence/privacy-sandbox-2026-11-01/linux-workflow-initial.json), [successful isolated tools](evidence/privacy-sandbox-2026-11-01/linux-workflow.json).

## 5. macOS can deny reads, but a private filesystem is not a private OS

Native Seatbelt is the most direct candidate for preserving the existing Mac execution environment. A launch wrapper can restrict reads by the official process and inherited children. It does not provide Linux-style mount namespaces that transparently remap selected files. Read denial and path redirection are different capabilities. Anthropic's own runtime source notes that its macOS credential-file masks degrade to denial because SBPL cannot redirect reads. Its normal policy also permits substantial system information. Adopting that runtime unchanged would not establish the desired privacy boundary. [Anthropic runtime source](https://github.com/anthropics/sandbox-runtime/blob/main/src/sandbox/macos-sandbox-utils.ts).

Custom Seatbelt policies carry a support tradeoff: Apple DTS says SBPL is undocumented for third-party use and custom policy behavior is an implementation detail. This is a reason for a small maintained policy and upgrade regression tests, not evidence that native isolation is impossible. Apple's supported alternatives include App Sandbox, Endpoint Security and virtualization. [Apple DTS explanation, updated September 2026](https://developer.apple.com/forums/thread/777509).

App Sandbox is not established as a drop-in launcher for arbitrary official binaries with their existing signing and entitlements. Apple's supported embedded-tool contract involves sandbox inheritance entitlements. Re-signing vendor binaries is outside the vanilla requirement. Endpoint Security can authorize some filesystem/process events, but entails a separately entitled system component and user approvals; it is not a generic replacement for OS-information virtualization. Neither is selected as new AI Manager machinery. [App Sandbox embedded tools](https://developer.apple.com/documentation/security/protecting-user-data-with-app-sandbox), [Endpoint Security](https://developer.apple.com/documentation/endpointsecurity), [installation requirements](https://developer.apple.com/videos/play/wwdc2020/10159/).

The [Mac experiment](../../scripts/privacy-macos-sandbox-feasibility.py) and [follow-up probes](evidence/privacy-sandbox-2026-11-01/repro/README.md) ran on a fresh rented Apple-silicon Mac with macOS 26.7, kernel 25.6.0, native Command Line Tools and independent web-egress denial. All model responses and credentials were synthetic. No provider account, browser, personal Mac or personal file was used. The exact binary hashes and platform are in the [manifest](evidence/privacy-sandbox-2026-11-01/mac-manifest.json). The fixture observer stayed outside the policy; official clients and their tool children entered it before execution.

## 6. Shared settings and credentials are still a design problem

An isolated view can preserve an absolute pathname while changing what resides there. That makes virtualization worth investigating for the relative-path issue in plan section 4.2. It does not automatically preserve the mixed ownership of a Codex home: shared settings/history coexist with account-private auth, installation IDs, caches, locks and encrypted secrets.

The measured `EBUSY` result rules out the naive design of mounting a single shared `config.toml` or mutable `auth.json` into every private home. Native atomic replacements need their containing directory. An external replacement can also leave a running file bind pointing at the older inode; that latter behavior is a filesystem design concern, not an additional measured result here. Codex deliberately resolves configuration symlink write targets before its atomic write, which differs from a file mount and must be preserved. [Codex config writer](https://github.com/openai/codex/blob/54201ea65a3501d09a87c776376a0c16aa39db70/codex-rs/core/src/config/edit.rs).

An additional offsite Linux experiment now confirms the symlink tradeoff in the official binary. Three synthetic homes read the same linked config containing `model_instructions_file="../instructions.md"`, `sqlite_home="."` and `log_dir="."`. The sibling home retained the instructions path but changed the database/log paths. The deeper home attempted the instructions path under its own parent and returned a configuration error; its app-server logged that it was falling back to defaults. The native `features disable shell_snapshot` command did preserve the config symlink, atomically replace the canonical file and expose the edit to an already-running owner. Shared native writes therefore work, but the shared file alone does not preserve relative-path meanings. No personal settings were used. [Native config results](evidence/privacy-sandbox-2026-11-01/linux-config-layout.json), [probe](../../scripts/privacy-config-layout-audit.py).

Binding an entire shared directory preserves its atomic replacement behavior but shares everything in that directory unless another boundary separates it. Copying config into each home loses live shared edits; a private writable overlay can do the same. A custom filesystem could express more selective behavior, but adds a substantial new component and is not the default recommendation for minimizing workflow impact.

Keychain and encrypted-secret migration remain separate. Keeping the same visible home path in multiple isolated processes while exposing the same keychain can recreate a shared credential key. Moving to another OS user or guest can make legitimate existing secrets unavailable. No blanket keychain block, secret deletion, copied encrypted blob or fallback to a different credential-store mode is accepted as a transparent fix. The account-private auth lock and race requirements remain unchanged.

## 7. Native tool bridges need a narrower claim

Keeping a provider-facing client in a VM while giving it native tools can reduce the client's automatic access to host state. It can still be useful under the accepted risk from malicious tools. It is not proof that host information cannot reach the provider: an unrestricted host shell or filesystem service can return that information as tool output, which the client then sends with the task.

Codex has an experimental execution service and direct endpoint support. Its vendor registration/relay mode is unnecessary for this proposal; the candidate would use a direct local/private transport. The simple `CODEX_EXEC_SERVER_URL` switch suppresses implicit shared-daemon attachment. Source also supports `CODEX_HOME/environments.toml` with a remote default, which avoids that particular switch and offers a candidate for retaining the guest's ordinary shared daemon. That alternative has not been demonstrated with the official test binary. R15 now removes shared-daemon preservation as a reason to pursue it; no new executor/guest service is selected. [Execution service](https://github.com/openai/codex/blob/54201ea65a3501d09a87c776376a0c16aa39db70/codex-rs/exec-server/README.md), [daemon selection](https://github.com/openai/codex/blob/54201ea65a3501d09a87c776376a0c16aa39db70/codex-rs/tui/src/daemon_startup.rs), [environments configuration](https://github.com/openai/codex/blob/54201ea65a3501d09a87c776376a0c16aa39db70/codex-rs/exec-server/src/environment_toml.rs).

The service already covers native process execution, stdin/PTY handling, filesystem operations, apply-patch and delegated HTTP; explicitly environment-owned hooks and MCP also have native paths. This makes it a substantive option for retaining Mac builds and live repository edits. It changes which process observes the OS for the model client's User-Agent and installation ID: a guest-side request owner would observe guest state unless host values are forwarded. That is a source-based inference to verify in captures, not proof of a tested deployment. [Execution protocol](https://github.com/openai/codex/blob/54201ea65a3501d09a87c776376a0c16aa39db70/codex-rs/exec-server-protocol/src/protocol.rs), [request metadata owner](https://github.com/openai/codex/blob/54201ea65a3501d09a87c776376a0c16aa39db70/codex-rs/login/src/auth/default_client.rs), [installation identity owner](https://github.com/openai/codex/blob/54201ea65a3501d09a87c776376a0c16aa39db70/codex-rs/core/src/installation_id.rs).

Remote execution still changes concrete workflows in the pinned source:

- TUI and `exec --worktree` reject a remote default; managed worktree creation and in-session working-directory changes are also rejected. This is an existing feature loss, not an abstract risk. [TUI startup](https://github.com/openai/codex/blob/54201ea65a3501d09a87c776376a0c16aa39db70/codex-rs/tui/src/startup_orchestration.rs), [exec startup](https://github.com/openai/codex/blob/54201ea65a3501d09a87c776376a0c16aa39db70/codex-rs/exec/src/lib.rs), [managed worktrees](https://github.com/openai/codex/blob/54201ea65a3501d09a87c776376a0c16aa39db70/codex-rs/tui/src/app/managed_worktree_creation.rs), [directory changes](https://github.com/openai/codex/blob/54201ea65a3501d09a87c776376a0c16aa39db70/codex-rs/tui/src/app/working_directory.rs).
- MCP declarations default to the client's local environment. Executor-bound stdio and HTTP support exists, but existing native MCP ownership does not transfer automatically. Executor stdio requires explicit cwd and UTF-8 command data. Ordinary hooks also remain client-local unless environment-owned. [MCP environment default](https://github.com/openai/codex/blob/54201ea65a3501d09a87c776376a0c16aa39db70/codex-rs/config/src/mcp_types.rs), [stdio launcher](https://github.com/openai/codex/blob/54201ea65a3501d09a87c776376a0c16aa39db70/codex-rs/rmcp-client/src/stdio_server_launcher.rs).
- An execution session detached by connection loss is retained for 30 seconds; after expiry the server removes it and shuts down its process handler. Reconnection support is not proof of the existing background-work lifetime. Test both a brief interruption and one exceeding that window. [Execution session registry](https://github.com/openai/codex/blob/54201ea65a3501d09a87c776376a0c16aa39db70/codex-rs/exec-server/src/server/session_registry.rs).

Executor initialization supplies native home, cwd, shell path and platform to the client; environment configuration supplies hostname for requirement matching. These are executor-to-client observations, not proof that every field reaches OpenAI. The model environment prompt explicitly renders cwd and shell name. The executor build identifier derives from commit/build target and is not itself a machine-specific hardware ID. [Initialization fields](https://github.com/openai/codex/blob/54201ea65a3501d09a87c776376a0c16aa39db70/codex-rs/exec-server-protocol/src/protocol.rs), [native configuration and hostname](https://github.com/openai/codex/blob/54201ea65a3501d09a87c776376a0c16aa39db70/codex-rs/exec-server/src/environment_config.rs), [model environment context](https://github.com/openai/codex/blob/54201ea65a3501d09a87c776376a0c16aa39db70/codex-rs/core/src/context/world_state/environment.rs).

The native execution service is itself vendor code outside the guest. Its startup loads configuration, initializes optional OpenTelemetry and constructs an HTTP client; it also prepares native skill/plugin discovery. A direct endpoint avoids hosted registration, but does not remove the need to audit this native process's own filesystem reads, idle traffic, account state and lifetime. [Execution-service startup](https://github.com/openai/codex/blob/54201ea65a3501d09a87c776376a0c16aa39db70/codex-rs/exec-server-cli/src/command.rs), [capability preparation](https://github.com/openai/codex/blob/54201ea65a3501d09a87c776376a0c16aa39db70/codex-rs/exec-server/src/discoverV2/capability_manager.rs).

This option is useful research for reducing the client's automatic access to native machine data. It does not presently satisfy the full workflow contract, and it is not selected as a workaround.

The same distinction applies to MCP and any services required by its retained tools. GUI automation and extra integration parity are now excluded; original Chrome CDP sign-in remains explicitly required. Their reach must be counted honestly; they are not a reason to build a new malicious-tool security system or remove existing functionality without a decision. Launching an unrestricted host service to work around every denied operation would erase the useful boundary.

## 8. Existing VM products are candidates, not automatic replacements

Apple's `container` runs Linux workloads in lightweight VMs on Apple silicon and currently supports macOS 26. It is relevant to a Linux-guest candidate, not native macOS process isolation. It does not by itself solve per-account identity, shared Codex state, browser binding, or the required proxy-failure behavior. [Apple container requirements](https://github.com/apple/container#requirements).

Docker Sandboxes already provides local microVMs, live worktree mounts at the same absolute paths and persistent guest state. Its default architecture also introduces host-side credential injection, shared skills and host MCP integration. Those are material differences from the approved vanilla/manual-login/proxy design and need review before adoption. The direct mounted worktree itself need not require a copied checkout or a new editor. [Docker workspace and network architecture](https://docs.docker.com/ai/sandboxes/architecture/), [Docker integration boundary](https://docs.docker.com/ai/sandboxes/security/).

Neither product was installed or benchmarked on a personal Mac. Resource overhead, build performance, filesystem watching, SQLite locking and device integration remain measurements to make on a selected candidate, not numbers inferred from marketing descriptions.
