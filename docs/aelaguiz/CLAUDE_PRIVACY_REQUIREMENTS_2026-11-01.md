## Potential privacy leaks and current protection

**The proxy protections are implemented; a complete boundary around Claude's own access to files and device information is not.** “Addressed” means an implemented control with recorded verification, within the scope stated below. Sandbox experiments do not count as completed product controls.

The addressed network and telemetry controls apply to accounts with privacy/proxy protection enabled. Ordinary accounts intentionally retain their normal route and existing telemetry environment. The later requirement to approve exact builds applies to every AIM-managed Claude account, but its enforcement is unfinished.

## Requirements already agreed

1. **Protect against unwanted disclosure to Anthropic.** Include services collecting on Anthropic's behalf. Restrict Claude's own automatic access to unrelated private state and device identifiers before vendor code starts. A separate config directory or a sandbox applied only to shell tools is insufficient. Inventory necessary functional metadata and identify any unavoidable disclosure explicitly.
2. **Preserve the native development workflow.** Keep normal commands, execution machines, project paths and live edits, model/effort, permission mode and basic terminal behavior. No daily privacy flags or new approval ceremony. Native Mac restrictions are the first candidate; moving development into a VM has not been approved.
3. **Keep the features Amir needs.** Preserve simultaneous same-account and different-account sessions, history/resume/forks, memory/instructions, skills, stdio/HTTP MCP and their required authentication/package dependencies, subagents, schedules/routines and legitimate background work. Retain AIM-owned scheduling hooks. Avoiding Codex's shared daemon does not authorize deleting Claude background functionality.
4. **Keep account identity separate without losing useful state.** Classify identifiers, credentials, caches and other state wherever stored. Do not copy or share another account's installation identity. Preserve legitimate same-account continuity, history and required MCP credentials. Any necessary identity change or reauthentication must be planned, not a surprise side effect. This does not require rotating identifiers every session.
5. **Keep proxy use optional and protected accounts fail closed.** Ordinary accounts must work without proxy infrastructure. Protected accounts use their assigned route for all Anthropic traffic, including initial browser sign-in. Missing or broken protection must never downgrade them to ordinary routing. Refuse startup or stop affected sessions with a clear error; do not switch accounts/proxies, replay work or silently reconnect. Healthy accounts continue.
6. **Remove unwanted telemetry and disable remote control.** Optional analytics, automatic error/diagnostic uploads and remote-control connections are distinct from requested model/task traffic. Verify every supported entry path and retained process, including saved enabled state. Losses caused by the agreed telemetry opt-outs are accepted.
7. **Execute only reviewed, explicitly approved Claude builds.** Check the actual executable/package and compatible privacy policy before all AIM-managed execution, including ordinary accounts, helpers, schedules, diagnostics and self-spawns. Disable automatic activation of unreviewed updates. Prepare an upgrade playbook that repeats collection, isolation and workflow checks. Isolated candidate review is distinct from approval for normal use.
8. **Prove both privacy and workflow preservation.** Cover Linux and rented macOS with synthetic fixtures first, then only sacrificial Claude proxy5/proxy6 through assigned routes where real-account testing is necessary. Real sign-in stays in the established original local Chrome instances. Never use a personal Mac as a sandbox test fixture. Stop all work on an actual human-verification challenge. Comment privacy-sensitive code and regression tests so future agents understand what must not break. Require cold review against the completed requirements and evidence before claiming completion.

## Accepted exclusions

Independent Figma, GitHub, Redis, registries and other services receiving their normal data are outside scope. Malicious tools, deliberate credential theft and privileged tampering are accepted risks; required tools remain useful. This does not exempt Claude's own automatic collection.

Optional personal hooks/plugins, terminal extras, realtime/voice and GUI/extra integrations need not be preserved. Required skill/MCP dependencies and AIM-owned routine hooks remain. No broad DLP/redaction system, extra Chrome firewall, replacement browser, fingerprint-spoofing system, TLS interception, credential broker or automatic failover is requested. Preserve the existing Chrome host, profile, cookies and proxy settings. The agreed scheduled transition remains available.

## Historical decisions and engineering work

**The ordinary-account proposal in this earlier discussion is superseded.** The implementation plan preserves ordinary Claude accounts' route and telemetry environment; it applies the new file/device protections to protected accounts. Exact-build approval, remote-control disabling and the subsequently approved remote-feature-flag disabling apply to all AIM-managed Claude accounts. The earlier approval to disable telemetry globally was specifically for Codex.

The requirements discussion originally called for engineering to finish the Claude-specific file/API/request inventory, determine the smallest compatible access rules, specify identity migration and lifecycle enforcement, and enumerate remaining functional metadata. Any necessary workflow reduction or unavoidable disclosure must be brought back for a decision rather than silently accepted.

The implementation test plan must map every table row to evidence: positive collection baselines; outgoing-request captures; account separation and migration; forbidden file/API reads including inherited handles; proxy-down startup and mid-session loss; all remote-control entry paths; approved/unknown/replaced builds and updates; concurrent sessions, resume/history, skills/MCP, native tools and scheduled/background work. Compare against the existing working baseline, test failure and restart, and preserve evidence without publishing private identifiers. This is a requirements draft, not a completed implementation specification or test sign-off.
