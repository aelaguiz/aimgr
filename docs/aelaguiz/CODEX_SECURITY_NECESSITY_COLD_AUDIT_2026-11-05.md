# Codex privacy: what was necessary and what was excessive

**Verdict: the privacy core is justified, but the implementation is overbuilt around launch admission and settings recovery. The screenshot failure is a consequence of the vendor filesystem boundary, and fixing that boundary matters more than the smaller code cuts.** Account-directory isolation is an explicit requirement. The exhaustive startup filesystem allowlist is the selected implementation; the supplied user statements do not independently approve every restriction it creates. Keeping every restriction because it appears in the plan would preserve an actual workflow failure.

The current code does **not** repeat Claude's former blanket restriction on ordinary tools. It does restrict Codex's built-in operations, including operations the user deliberately requests. An OS file rule cannot distinguish Codex automatically inspecting a file from its built-in image reader opening that same file on request. That is the central mismatch between the chosen mechanism and “I want my shit to keep working.”

Do not adopt [privacy PR #14](https://github.com/aelaguiz/aimgr/pull/14) unchanged. Retain the credential, identity and diagnostic protections. Resolve the screenshot access boundary, remove unnecessary launch coupling, and simplify recovery where it exceeds the actual writers that must be supported. There is no evidence here that deleting all native helpers, MCP migration or process-related code would preserve the agreed requirements.

**The screenshot failure exposes a real architectural cost.** The read-only [adoption comparison](</Users/aelaguiz/.aws/aimgr-macos-test/CODEX_WORKFLOW_ADOPTION_REVIEW_2026-11-05.md>) records stock and protected runs using the same official Codex 0.166.0 on the isolated Linux VM and rented Mac. Stock reads both project and `/tmp` images. Protected Codex reads the project image and refuses the `/tmp` image. Both conversations exit zero. This is observed incompatibility, not a hypothetical attack or an inference from a deny rule.

The reason is visible in the implementation:

- [Startup input selection](https://github.com/aelaguiz/aimgr/blob/7c4eccb9a00ad62a3119f35ec9531091aed97f9e/src/privacy/codex-launch-inputs.js#L61) admits projects, explicit startup images/files, selected configuration assets and necessary runtime paths. It does not admit an arbitrary image selected later.
- The [Linux launcher](https://github.com/aelaguiz/aimgr/blob/7c4eccb9a00ad62a3119f35ec9531091aed97f9e/native/codex/approved_launch_linux.c#L97) gives the vendor an allowlist. The [Mac launcher](https://github.com/aelaguiz/aimgr/blob/7c4eccb9a00ad62a3119f35ec9531091aed97f9e/native/codex/approved_launch_macos.c#L112) denies vendor reads outside the selected paths. A private invocation temp directory is allowed; the shared temp root's contents are not.
- The official [image handler](https://github.com/openai/codex/blob/6ff1e1ca3b30fc8b914720681fcf5fe62e95f856/codex-rs/core/src/tools/handlers/view_image.rs#L144) resolves the requested path and asks the filesystem implementation to read it. It does not become an ordinary shell executable that leaves the vendor policy.

This predicts similar failures for other vendor operations that open a later-selected outside file. It does **not** establish that every built-in operation fails, or that ordinary shell reads fail. Moving every screenshot into a project would change the workflow; it would not repair compatibility.

There is no demonstrated configuration-only mechanism that admits precisely the next requested image while denying automatic reads of that image to the same unchanged process. A shared `/tmp` read exception is a smaller change than removing file isolation, but it exposes other readable temp files to the vendor. An image-extension rule still admits unrelated images; it does not express user intent. A new interception broker would add machinery and conflict with this review's purpose. The honest choice is an explicit access exception or a relaxation of the general file-read boundary, followed by a small actual-client comparison.

**The process restrictions are narrower than their names suggest.** On Mac, ordinary executable children receive the [general `no-sandbox` transition](https://github.com/aelaguiz/aimgr/blob/7c4eccb9a00ad62a3119f35ec9531091aed97f9e/native/codex/approved_launch_macos.c#L109). Exact Codex/code-mode-host images retain the vendor filter. On Linux, ordinary tools receive [broad file, signal, ptrace, capability, namespace and other host permissions](https://github.com/aelaguiz/aimgr/blob/7c4eccb9a00ad62a3119f35ec9531091aed97f9e/native/privacy/launch_linux.h#L133), with explicit transitions for vendor reentry. They retain AppArmor labels; they are not generally confined to the vendor's file roots.

Linux's inherited [seccomp listener](https://github.com/aelaguiz/aimgr/blob/7c4eccb9a00ad62a3119f35ec9531091aed97f9e/native/privacy/launch_linux.h#L375) denies vendor `uname` and permits ordinary-tool `uname` after checking the current profile. On x86, compatibility-ABI calls also pass through the listener. This adds a helper and a potential compatibility/performance dependency; it is not a broad signal or process-inspection ban. The helper survives while filter users remain, so it can outlive the foreground session with legitimate background work.

The separate [process-control executable](https://github.com/aelaguiz/aimgr/blob/7c4eccb9a00ad62a3119f35ec9531091aed97f9e/native/codex/process_control.c#L1) only inventories processes for explicit MCP conversion. The current code does not signal them. Earlier worklog descriptions of termination, scheduler pausing, reboot fences and updater attestation describe superseded implementation. They should not be presented as restrictions still in this PR.

The seven-day maximum in [offsite-test authorization](https://github.com/aelaguiz/aimgr/blob/7c4eccb9a00ad62a3119f35ec9531091aed97f9e/src/privacy/artifact-admission.js#L176) is another invented limit. **The large simplification concerns the host-read boundary, not account-directory isolation.** These are separate choices. Private account homes can remain while the general filesystem rule changes. The supplied record does not show direct user approval of every host-path deny; equally, this audit cannot promise identical privacy after removing those denies. Two changes deserve a concrete boundary decision:

1. **Permit requested files outside the startup grants.** The immediately useful choice is a temp-root read exception for the existing screenshot workflow. I recommend accepting that specific exposure before considering removal of the whole filesystem policy. Retain private auth/other-account isolation, targeted identifier denials and diagnostic shutdown. Validate `/tmp` image reading alongside a forbidden private-file canary on both platforms. Existing Mac temp-directory metadata permission is not permission to read its contents.
2. **If a much smaller system is the priority, retain account-directory isolation and target the demonstrated automatic collectors.** That could remove much of the exhaustive file inventory and saved-picker prediction. It also gives the vendor access to other ordinary readable files. This changes the chosen protection's coverage, so the proposed exposure needs explicit user agreement; it does not inherently undo the approved private-account layout. The current audit does not claim that targeted denials can prove absence of every future automatic collector. It is not necessary to decide this larger question to repair screenshots.

The settings adapter and MCP conversion are not honest wholesale cuts while retaining private homes, shared relative settings, unchanged native editing, native rotating-token concurrency and an unmodified client. Those requirements interact. An asynchronous copy of each account's File credentials can replay an already spent refresh token even when the accounts share the native lock: the lock does not refresh the stale file's contents. A symlink fails the official File writer. Replacing this with a broker would expand the system. The finite keyring conversion is the established working mechanism.

**The earlier acceptance was substantial but did not answer necessity or actual adoption.** The [acceptance record](https://github.com/aelaguiz/aimgr/blob/7c4eccb9a00ad62a3119f35ec9531091aed97f9e/docs/aelaguiz/CODEX_PRIVACY_M1_ACCEPTANCE_2026-11-04.md#L3) says the final cold review closed privacy and overbuild findings. The later screenshot comparison disproves a broad reading of its compatibility verdict. It does not invalidate the genuine HTTP/WebSocket, refresh, native MCP, reviewer, Chrome or concurrency observations.
