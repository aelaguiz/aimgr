# Claude and Codex privacy inventory

**Claude and Codex can identify installations and accounts, collect machine details, and send information outside the task itself. Separate account homes and telemetry opt-outs cover only some of those paths.** This is the canonical inventory of those mechanisms and the protections actually supported by evidence.

Amir considers unwanted identification, tracking and disclosure a privacy violation regardless of the vendor's terminology or justification. That is the standard used here. Describing a mechanism does not establish the vendor's motive. Necessary task content and explicitly accepted workflow exceptions are identified separately so an investigation does not silently become permission to restrict normal work.

Last updated: **November 7, 2026**. The initial investigation combines independent Claude, Codex and fleet/AIM reviews, exact source inspection, existing isolated experiments and official documentation. Actual credentials, device IDs, account IDs, browser state and personal transcripts are not reproduced here. The initial technical inventory has a separate [cold review](aelaguiz/evidence/privacy-inventory-2026-11-05/cold-review.md). The later [Codex security-necessity audit](aelaguiz/CODEX_SECURITY_NECESSITY_COLD_AUDIT_2026-11-05.md) distinguishes required protections from unnecessary restrictions and supporting machinery. Follow-up work is tracked in the [AIM worklist](../WORKLIST.md) and its linked GitHub issues.

## Allowed and disallowed access

**Give agents broad access to the places work happens, without granting the whole home directory or disk.** A file does not need to be predicted at session startup or belong to the current repository. The working directories include their subdirectories and files created later. System/runtime access and the existing credential integrations still need to work; this does not authorize reinstating the blanket child-process sandbox restrictions removed from Claude.

The November 5 directory decision and comparison of both providers are recorded in [right-size Claude and Codex privacy (#16)](https://github.com/aelaguiz/aimgr/issues/16). It replaces the proposed unrestricted host-file access with a broader working-directory allowlist. Exact screenshot locations can differ by machine; selecting one must not silently grant its entire enclosing home directory or disk.

**The native file boundary and ordinary tool permissions differ.** The reviewed launchers constrain built-in and automatic vendor reads while ordinary shell, browser and MCP executables retain broader OS access. The instruction not to evade the work boundary through a helper is an agent-behavior requirement, not an OS guarantee against malicious tools. The right-sizing issue preserves this distinction and the earlier removal of blanket child-process restrictions. The Claude implementation in [issue #21](https://github.com/aelaguiz/aimgr/issues/21) applies privacy independently of proxy assignment and keeps the primary login on each machine. The native acceptance described in the [plan](CLAUDE_PER_MACHINE_PRIVACY_AND_LOGIN_2026-11-07.md) is still required.

### Allowed

1. Read, create and edit task files throughout the workspace directory, across repositories, plus `/tmp`, Downloads and the configured screenshot directories. Apply normal OS permissions and the task's ordinary editing/deletion rules. Physical aliases such as macOS `/private/tmp` refer to the same approved directory.
2. Open images and other files in those directories at any point in a session, including files produced by browsers, tools or other agents after launch. Do not require per-file approval, relocation into the project or a session restart merely because the path was not known at startup.
3. Preserve previously trusted Claude project roots, subject to the existing home and ancestor exclusions, and add another working directory when the user selects it for work. A selected file outside those directories permits that file, not an implicit grant to its whole parent tree.
4. Run normal shells, builds, debuggers, process inspection, background jobs and task-related service operations. Preserve ordinary runtime and dependency access, browser workflows, MCP, SSH, SDK credentials and native Keychain use through their existing mechanisms. These operational needs are not permission to browse unrelated personal data.
5. Preserve concurrent sessions, nested agents, independent reviewers, scheduled work, shared history, skills, instructions and editable shared settings, including relative paths.
6. Send task-relevant prompts, files, images and tool results to the model provider. Real paths or machine details can be included when the task calls for them. Files placed in an approved working directory are within the readable work area, even if their contents are personal; the directory rule is not a content classifier.

### Disallowed

1. Grant the entire disk or home directory by default, or browse unrelated personal documents, photos, mail archives, backups and private application data merely because the OS user can read them. Do not use a shell or helper to evade the agreed work-area boundary. Preserve normal tool/runtime access rather than imposing a blanket child-process jail.
2. Collect or transmit stable host identifiers in the background for tracking, including hardware serials/UUIDs, system machine IDs and MAC addresses. Task-requested diagnostics and the previously accepted mount-information/Keychain exceptions remain distinct from background collection.
3. Send optional vendor analytics, diagnostics, crash reports or telemetry, including vendor diagnostics configured for a custom collector. Keep generic `OTEL_*` settings available to ordinary task tools.
4. Copy or share primary account login tokens between machines or accounts, or reuse AIM-managed installation identifiers across account environments. Intended shared third-party MCP credentials remain supported.
5. Automatically reuse an existing conversation identity under another account. Rotating continuation creates fresh thread/session IDs; the existing explicit manual command retains its warning.
6. Bypass an assigned proxy, silently fall back to a direct connection, enable vendor remote-control services or replace the reviewed vendor executable through unattended self-update.

## Evidence and scope

### How to read an entry

**Captured** means an isolated test observed the outgoing field or request. **Read observed** means a trace or paired test established local access; upload is a separate question. **Source** means the inspected version contains the described producer, storage or sender. **Documented** means the vendor describes it, without a matching local capture. **Inference** means the mechanism permits the stated association but the provider's use of it was not observed. **Unknown** names missing evidence rather than assuming safety or a leak.

An app-generated installation ID is different from a hardware serial/UUID, an OS machine ID, an account ID and a conversation ID. A random identifier can still track a long-lived installation. Hashing or truncating an identifier can preserve linkability. A file that the app can read is not automatically a file it uploads; a value absent from one capture can still have another sender or a derived form.

“Protected Claude” below means the reviewed AIM protected-account path, not every Claude process or every account. “Codex milestone 1” means the reviewed implementation in [privacy PR #14](https://github.com/aelaguiz/aimgr/pull/14), at `7c4eccb9a00ad62a3119f35ec9531091aed97f9e`; optional routing is [proxy PR #15](https://github.com/aelaguiz/aimgr/pull/15), at `31aa23ab9c3902129b6aba526ea225a7b32ae52b`. These names must not be substituted for the installed state in the next table.

### Machine, terminal and environment information

1. **Linux host machine ID.** Existing trace actually opened `/etc/machine-id`. Reviewed source uses it with `/proc/self/ns/pid` to construct local `pidDomain`; reviewed session/UDS/auth-lock consumers did not serialize it to provider. This is proven read, not proven upload. Protected file policy denies host-ID paths, including alternate D-Bus path tested later. 2.1.317 candidate controls deny six previously readable paths: relative path, symlink, kernel version, kernel release, hostname and D-Bus machine ID. DMI UUID was already unreadable in baseline and is not counted as an AIM success. `claude-metadata-inventory.json`, candidate verification T05/T06 and `upgrade317_reads/result.json` reference.
2. **Exact OS/kernel version.** Vanilla auto system context uses `os.type`/`os.release` and sends `OS Version`. Protected baseline examples become `Linux` or `Darwin unknown`. M5 2.1.317 native policy blocks version paths before vendor startup; it does not redact an explicit `uname` tool result or user task context. Exact version appeared in ordinary error-control model requests, intentionally outside protected scope.
3. **macOS exact native denials.** `native/claude/approved_launch_macos.c:369` denies IOKit properties `IOPlatformUUID`, `IOPlatformSerialNumber`; sysctls `kern.hostname`, `kern.osproductversion`, `kern.osrelease`, `kern.osversion`, `kern.version`, `hw.model`; `/System/Library/CoreServices/SystemVersion.plist`; Unix `gethostuuid`; Mach `host_kernel_version`; vendor execution of `/usr/bin/sw_vers`. Policy is vendor-scoped; ordinary tools retain discovery.
4. **Foundation hostname residual.** Candidate review explicitly finds Foundation can still return a nonempty hostname, sometimes equal between baseline/protected probes. The exact candidate's reviewed automatic consumers use `os.hostname`/native `gethostname`, whose restricted failure returns `unknown`; no automatic Foundation consumer found. Candidate comparisons found no recovered hostname in protected requests. This is a residual readable API, not reliable full-hostname denial, not demonstrated protected upload. An unwrapped RC positive control did send current hostname once. Source and receipts are in candidate report “Foundation hostname observation” and later capture comparison.
5. **Hostname local uses.** `.oauth_refresh.lock.owner.pidSpace` and `fullscreenBootPending[pid].host` are local coordination/crash state. The reviewed fullscreen event sends strike/count/time, not hostname. Live lock records must not be treated as freely rotatable installation IDs.
6. **Terminal identity.** Source reads `TERM_PROGRAM_VERSION` and terminal query **XTVERSION `CSI > 0 q`**; optional event `tengu_terminal_probe` has `xtversion`/`term_program_version`. Ordinary positive controls emitted synthetic canary in analytics; protected lifecycle/interactive captures suppressed it. No functional-model serialization found on tested Claude paths. This differs from Codex's observed terminal User-Agent. Local debug may retain terminal data. Protected settings clear `HOSTNAME`, `TERMINATOR_UUID`, `TILIX_ID`, `GNOME_TERMINAL_SERVICE`; preserve `TERM` and required environment.
7. **Bundled host detector.** Code includes OTel `hostDetector` probing `ioreg -rd1 -c IOPlatformExpertDevice`/`IOPlatformUUID`, attributes `host.name`,`host.arch`,`host.id`. Reviewed actual OTel builder selected `osDetector`/`envDetector`; hostDetector references were definitions/re-exports. Bundled capability is not evidence it ran. No claim hidden hardware attestation was demonstrated.
8. **Built-in plugin env analytics.** Source invokes `uname -s/-r/-m` and reads `/sys/hypervisor/uuid`, producing event fields `linuxKernel`,`linuxDistroVersion`,`architecture`, deployment classification. Reviewed `DISABLE_TELEMETRY` check precedes context construction. Existing ordinary controls collected; protected startup/tool-failure/idle/shutdown controls suppressed reporter. Tools themselves still can discover platform information.
9. **Accepted functional metadata remains.** Captured headers include `User-Agent: claude-cli/<version> (external, sdk-cli)`, `X-Stainless-Arch`, `X-Stainless-OS`, `X-Stainless-Runtime`, `X-Stainless-Runtime-Version`. Platform, shell, cwd, date, Git status/paths, prompt, source and requested tool output are task context. Broad OS family/CPU architecture/client/runtime version are distinguishable from a unique hardware/install identifier. Wrapper does not make user anonymous.
10. **File/environment authority.** Protected vendor sees private config, initial cwd/known trusted projects, required instructions/imports, memory, skills/MCP package/auth/TLS dependencies and selected system paths. It cannot automatically read whole home/other account collection under tested boundary. `resolveClaudeTaskReadRoots` excludes whole home roots, resolves symlink/import targets, and grants stored trusted project directories, not merely current cwd. Required build/MCP env values remain vendor-readable: no blanket secret vault. Arbitrary inherited FDs are closed at final entry; environment crosses trusted launcher in owned unlinked regular file then FD closes. Source: [claude-launch-inputs.js](../src/privacy/claude-launch-inputs.js), [claude-mcp-inputs.js](../src/privacy/claude-mcp-inputs.js), [claude-instruction-inputs.js](../src/privacy/claude-instruction-inputs.js), native launchers.
11. **Tool boundary is deliberately broad.** Nov 3 macOS rollback causes ordinary program exec to leave vendor Seatbelt policy, allowing Chrome's own sandbox and normal shell/MCP/developer behavior. Direct vendor self-spawn retains policy; nested AIM reenters selected account boundary. Linux tools profile permits broad files with snapshot/update common restrictions and controlled vendor reentry. Intentional tools can read personal files or identify host and return data to model; accepted risk, not an AIM claim of universal descendant isolation.

Authenticated model, usage, feature, connector and refresh requests necessarily identify the selected account through bearer credentials and account metadata. New local OAuth grants do not hide that the underlying account is the same account. Reusing one refresh lineage across environments lets the issuer link those environments. M1 keeps Codex CLI primary grants local, fences native refresh by underlying account/environment/generation and prevents publishing/hydrating these grants through the legacy globally shared pool. Separately scoped Prime/Pi callers retain their legacy credential authority; do not call them covered by Codex CLI isolation. Browser sign-in remains an independent identity surface with existing cookies/profile and its own connection route.

#### Data-handling policies remain separate from client opt-outs

Official OpenAI documentation states that ChatGPT sign-in follows ChatGPT workspace controls, while API-key usage follows the API organization's retention and data-sharing settings. AIM's local analytics/exporter opt-outs do not select a training preference, establish a zero-retention agreement, or delete data already held by OpenAI. No authenticated account/workspace data-sharing setting was inspected in this investigation, so the current effective policy for each pooled account remains unverified. This is separate from proving which bytes the CLI sends. [Official OpenAI authentication and policy scope](https://learn.chatgpt.com/docs/auth#openai-authentication).

#### Cookies and network fingerprint

Native HTTP and WebSocket transports share a **process-global, memory-only** ChatGPT infrastructure cookie jar. Configured cookies are factory-scoped. Server-minted cookie values can correlate requests in one process even when not an account cookie. The code does not show these cookies being persisted to a global disk cookie file. AIM standalone private processes reduce reuse across account owners; no claim is made that M1 removes this native jar. ### MCP, browser, remote control and ordinary tools

MCP is an independent data recipient. Local stdio servers execute on the user's machine; remote MCP clients contact their configured service with OAuth/bearer auth, initialization data, tool arguments and resource requests. Tool schemas/results become model context as needed. A connector account's identity is independently known to its service; preserving the same MCP credential under multiple OpenAI accounts preserves that connector-level linkage. Plugins can install skills, hooks, MCP definitions and executable helpers. Feature inventories and selected tool namespace/function descriptions also appear in model request metadata; `mcp_attribution` is a bounded, model-invisible request attribution structure for eligible internal paths. Disabling analytics does not remove this ordinary service use. Do not describe MCP as anonymous or covered solely by OpenAI telemetry controls.

Remote-control enrollment is an additional network owner: selected auth/account, CLI installation ID, hostname/server name and host-device kind reach enrollment/refresh/relay endpoints; state DB stores enrollment metadata and enabled state. Server-issued enrollment/pairing values include `server_id`, `environment_id`, pairing codes and expiry; remote stream/client identifiers are additional relay protocol state. These are distinct from AIM's locally provisioned environment anchor. M1 disables it through native requirements plus `CODEX_INTERNAL_APP_SERVER_REMOTE_CONTROL_DISABLED=1`, avoids shared daemon attachment and selects standalone TUI behavior (`--no-daemon`) or invocation-owned stdio app-server/exec where required. M1 intentionally does not preserve automatic remote-control/daemon features. The caller parser rejects disallowed daemon/remote entry points before vendor execution. [Remote enrollment API](https://github.com/openai/codex/blob/6ff1e1ca3b30fc8b914720681fcf5fe62e95f856/codex-rs/app-server-transport/src/transport/remote_control/server_api.rs), [host-device header](https://github.com/openai/codex/blob/6ff1e1ca3b30fc8b914720681fcf5fe62e95f856/codex-rs/app-server-transport/src/transport/remote_control/host_device.rs), [AIM argument controls](https://github.com/aelaguiz/aimgr/blob/7c4eccb9a00ad62a3119f35ec9531091aed97f9e/src/privacy/codex-arguments.js).

Browser login is separate from Codex process telemetry: browser profile cookies, browser account identity, network route and original host remain observable. User explicitly preserved original Chrome/CDP profiles for true sign-in and assigned existing sacrificial routes for testing. M2 validates original bindings; it does not create a replacement browser, clone profiles or erase browser linkage. BrowserOS/other user-selected browser tools also have their own authenticated service state and can return personal data as normal tool results.

The M1 security model restricts the **exact reviewed vendor images** while ordinary shell/tool workflows retain normal OS access. It is intentionally not a general filesystem jail for the model or a data-loss-prevention filter. A tool can read a user-requested outside file, run `uname`, use an SDK key, operate Chrome or retrieve an OS fact and return it to the model. Automatic vendor collection is restricted; requested tool outputs are still sent as conversation content. This design is user-approved and essential for the retained workflow.

Two explicit vendor metadata exceptions remain:

1. **Linux:** vendor may read owner-matching `/proc/[0-9]*/mountinfo` and its fixed UID daemon-directory metadata so the unchanged native read-only sandbox can mask privileged socket aliases. This reveals mount topology/paths and is a local read; the exception alone is not proof of upload. Ordinary mounted-file contents remain governed by their own grants.
2. **Mac:** the selected User-domain default Keychain database, its native atomic-replacement/lock names and security preferences are admitted so native MCP Direct keyring can read/refresh. Its legacy filename counterpart is metadata-only, unrelated databases remain denied, selected database xattrs remain denied, parent directory is not broadly granted and native item ACLs remain authoritative. **This is database-level filesystem access, not a Codex-item-only filesystem guarantee.** There is no proof here that Codex enumerates unrelated keychain items; do not imply the filesystem policy could prevent all such item-level access within the admitted DB. Native fixture tested denied/read-authorized import, five refreshes, cross-account homes and logout/nonresurrection.

The known `/tmp` screenshot limitation belongs in the inventory: M1 vendor access is built from selected startup inputs plus private scratch. Calling built-in `view_image` on an image another tool wrote under an unrelated `/tmp` location can be denied because that built-in read is vendor code. This is observed behavior recorded in the November 5 workflow audit, not a new reproduction for this inventory. Ordinary shell/image tools retain their access. No fix or workaround was applied here.

### What the reviewed Codex protection covers

The proposed M1 implementation covers exact-artifact admission, private local primary auth and installation IDs by account/environment, selected vendor file/metadata restrictions, mandatory telemetry/feedback/remote-control shutdown, shared settings/history/MCP continuity, correct account ownership during concurrency and native refresh. Its Mac/Linux acceptance record has source review plus actual native collector and workflow evidence. M2 adds optional assigned routing and no-direct-fallback enforcement with recovery semantics. These are **results for the reviewed implementation**. They must remain distinct from older installed AIM/client combinations on the fleet.

Remaining correlation/disclosure channels include:

- Underlying OpenAI account identity and issuer-side OAuth/refresh/account history.
- Original browser identity/cookies, shared IP/proxy exits, network timing and transport fingerprint.
- Ordinary model request IDs/metadata, workspace paths, Git remotes/commit/dirty state, tool inventory and platform/version context.
- Shared prompts/history/memories, retained compaction content, exact code/task text and user-requested tool output.
- Deliberately shared MCP/service accounts, independently authenticated plugins/apps and arbitrary ordinary-tool networking.
- The approved Keychain and mountinfo exceptions; not item-scoped identity isolation.
- Organization-supplied remote policy, the independent closed-source desktop app, old already-running clients and direct launches outside the admitted AIM path.
- Version drift. Native settings/state/transport changes require artifact-specific review; a matching CLI family/name is insufficient.

## What AIM shares and what separate homes accomplish

**Account separation, machine separation and anonymity are different properties.** The table describes what the mechanism establishes, without treating one as evidence of the others.

| Mechanism | What it separates | What it leaves linkable |
| --- | --- | --- |
| Separate application home and installation ID | Different account installations can present different client IDs. | The same underlying account, shared content, browser identity and network origin. |
| Separate login on each machine | Each environment has its own authorization and refresh lineage instead of receiving a copied grant. | The provider still knows both logins belong to the same account. |
| New thread/session IDs on account rotation | Removes the explicit reuse of those conversation IDs. | Retained text, opaque server payloads, repository metadata and timing. |
| Assigned proxy | Changes the network exit visible to covered destinations. | Account/device IDs, content, shared exits, browser state and transport characteristics. |
| Telemetry opt-out | Suppresses the particular reporter/exporter controlled by that setting. | Functional API metadata, model input and other reporting channels. |

### The credential pool is another sensitive state owner

Managed Claude and Codex primary logins stay in the environment where each account signed in. Shared Redis holds allowlisted account metadata; it continues to hold separate legacy harness credentials, including the Prime/Pi Anthropic grant. Redis remains a sensitive coordination recipient, not an Anthropic or OpenAI telemetry destination. [Claude local credentials](../src/credentials/claude-local.js), [Claude metadata](../src/coordination/claude-metadata.js), [Codex local credentials](https://github.com/aelaguiz/aimgr/blob/7c4eccb9a00ad62a3119f35ec9531091aed97f9e/src/credentials/codex-local.js).

The older Claude bundle contained `claudeAiOauth` and `oauthAccount`, excluding installation-ID fields. That historical distinction does not make a copied primary grant per-machine authorization. The implementation and remaining validation are tracked in [per-machine Claude login and privacy (#21)](https://github.com/aelaguiz/aimgr/issues/21).

### Installed Codex shares substantially more than credentials

The installed AIM layout uses `~/.aimgr/codex-cli` by default and respects `CODEX_HOME`. Its current link helper shares most entries from the normal Codex home, excluding primary auth, installation ID and a limited set of control/temp/state-sidecar names. A newly introduced native top-level file can therefore become shared unless classified. On M5, Studio, M3 Max and M3 36 GB, inspected links share config, instructions, skills, sessions, `state_5.sqlite`, model cache, plugins and `.credentials.json` with `~/.codex`; primary `auth.json` and `installation_id` are separate regular files. File contents were not read. [Home links](../src/io/codex-home-links.js), [fleet receipt](aelaguiz/evidence/privacy-inventory-2026-11-05/fleet-metadata.json).

Installed AIM's Codex ID is deterministic from the normalized label. Reusing a label for a different underlying account can reuse the ID. The legacy ID writer also returns an error result instead of necessarily refusing the launch, and credentials and ID can be written into one rotating managed home. These source properties justify investigation of old launch/concurrency paths; this inventory does not claim a reproduced cross-account race. Milestone 1 assigns ownership to the underlying account and environment and has separate concurrency/refresh evidence. [Legacy ID writer](../src/targets/codex-installation-id.js), [legacy application](../src/targets/codex-cli.js), [M1 acceptance](https://github.com/aelaguiz/aimgr/blob/7c4eccb9a00ad62a3119f35ec9531091aed97f9e/docs/aelaguiz/CODEX_PRIVACY_M1_ACCEPTANCE_2026-11-04.md).

### Continuation intentionally retains identifying task content

Codex `resume-fresh` rewrites recognized identifiers and drops reasoning blobs by default, but its exact default is `dropReasoning: true, dropCompaction: false`. Encrypted compaction blobs survive to preserve continuation. The same default exists in installed main and both reviewed milestones. A provider-generated opaque blob can remain a correlation signal even after visible UUIDs change; actual provider correlation using that blob is **inferred, not observed**. `--drop-compaction` changes that behavior and is not silently enabled here. Explicit same-thread cross-account resume remains a warned manual command. [Copy policy](../src/targets/codex-thread-copy.js), [account-rotation intent](CODEX_CR_INTENT_VS_BUILT_2026-09-18.md).

Claude's cross-account copier remaps recognized structured session/message/tool/request identifiers and removes thinking/redacted-thinking blocks. It preserves the conversation. Unknown embedded identifiers, prose, files and exact task text can remain. Neither copier provides content anonymity or erases server-side history already received. [Claude transcript rekeying](../src/targets/claude-transcript-rekey.js), [resume selection](../src/targets/claude-sessions.js).

Claude project memory is deliberately shared through `CLAUDE_CODE_REMOTE_MEMORY_DIR` pointing to the ordinary local memory root. Codex milestone 1 deliberately shares instructions, skills, plugins, memories, sessions, history and native MCP credential ownership. A shared email in a memory, repository remote, source file, business document, browser result or MCP response can identify the same person across accounts or providers when used as context. Local sharing alone is not proof every file is uploaded. [Claude shared memory](../src/targets/claude-shared-memory.js), [Codex shared-state list](https://github.com/aelaguiz/aimgr/blob/7c4eccb9a00ad62a3119f35ec9531091aed97f9e/src/privacy/codex-account-state.js).

### Browser identity and network identity remain separate

Real sign-in uses the existing original local Chrome/CDP profile, retaining its cookies, login history and browser fingerprint. AIM validates the configured browser/profile/route and sets the reviewed site's analytics/marketing consent before navigation where implemented. It does not create an anonymous browser or move that profile into a test VM. Fresh CLI home directories cannot erase associations already present in the browser or at the provider. [Claude browser validation](../src/browser/claude-cdp.js), [Codex original-browser helper](https://github.com/aelaguiz/aimgr/blob/31aa23ab9c3902129b6aba526ea225a7b32ae52b/scripts/codex-login-browser.mjs).

Routing also has multiple recipients: provider, proxy operator, DNS resolver, exit-check service, package registry and requested third-party service. An assigned route changes what each can observe; it does not remove account credentials or request content. Existing route tests and their limits are linked in each app section. No route-health or packet-capture claim is made from the filesystem-only fleet inventory.

### The existing protection deliberately preserves normal work

These are accepted boundaries, not defects that authorize another round of restrictions:

| Accepted behavior | Remaining exposure |

| Ordinary shell commands, Chrome, developer tools, SDK keys, local agents and required MCP continue working. | Tools can read identifying information and return it to the model or their own services. Required inherited environment values remain readable by the vendor process. |
| Relevant source, instructions, memories, history and live settings remain usable. | Task context and content can identify the person, company or project. New out-of-grant path targets may require a new session. |
| Broad platform/architecture and functional protocol metadata remain. | These can still contribute to fingerprints alongside timing and content. |
| Original browser profiles and assigned proxies remain. | Browser/account history and shared network exits remain association signals. |
| Codex may read same-user Linux mount information. | Mount paths, device names and share names become locally readable; upload of the table was not established. |
| Codex may read/write the selected default macOS Keychain database and exact lock/replacement files for native MCP. | Unrelated service/account names are visible in database bytes; whole-database mutation is possible. Password encryption and native item permissions remain. |
| Organization-owned Codex policy is an approved gap. | The local review does not establish every server-controlled policy behavior over a session's lifetime. |

The November 3 Claude correction intentionally removed inherited restrictions from ordinary macOS tools. Reintroducing that broad restriction would contradict the accepted workflow boundary. Code-review-graph and Orca hook registrations were removed across the five machines at Amir's request on November 5; their historical presence is not a compatibility requirement. Other hooks and required integrations remain separate configured recipients. [Tool-boundary decision](aelaguiz/CLAUDE_TOOL_RESTRICTIONS_ROLLBACK_2026-11-03.md).

The per-machine implementation disables Claude-specific diagnostics, including detailed tracing, while preserving generic OTel settings for task tools; collector verification is pending. ### What this inventory does not yet establish

1. **Every installed version's complete behavior.** Four remote AIM checkouts and all inspected Codex command versions differ from the reviewed privacy setup. The fleet table records the exact difference. A source or test result for one binary cannot certify another.
2. **Every currently running owner.** This investigation did not enumerate and identify every live CLI, IDE, app-server, desktop or daemon process. Selected command paths do not prove their bytes or lifetime state.
3. **Every desktop, IDE, browser extension or third-party integration sender.** Installed hosts and documented/static mechanisms are included where inspected, but their full independent network/storage behavior needs its own evidence. CLI protection is not inherited automatically by the host application.
4. **Claude view-only session mirroring.** `autoUploadSessions` has source/schema/settings plumbing separate from Remote Control; its effective outbound caller and protection gate remain unresolved. No active upload is asserted.
5. **Complete denial of every hostname API.** The reviewed macOS Foundation residual remains locally readable; the inspected automatic Claude consumers and captured requests did not use it to disclose the hostname.
6. **Provider-side association, historical deletion or actual account retention/training choices.** The bytes and mechanisms establish possible join keys; they do not reveal how the backend uses them. No authenticated privacy settings were inspected.
7. **Unlinkability of retained compaction or task content.** Fresh visible IDs do not prove server-authored opaque payloads or shared content cannot be associated.
8. **A universal secret filter.** This work does not provide one. Required environment, intentional tool output, authored instructions, custom headers and third-party integrations remain real disclosure paths.

The Codex milestone-1 workflow review also found that built-in `view_image` cannot read unrelated `/tmp` screenshots used by existing QA workflows, on both isolated platforms. This is a compatibility defect, not a new privacy requirement or permission to restrict those workflows. The earlier full acceptance claim must be read with that later finding.

### Keeping the inventory current

A change to a client version, launcher, identity store, telemetry setting, proxy path or approved exception should update the affected mechanism here. Record the exact version/source, what is read, what is stored, what is actually sent, recipient and trigger, and the strongest available evidence. Keep unresolved branches explicit. Preserve historical receipts and explain what later evidence supersedes.

Actual tokens, identity values, browser profiles and personal logs do not belong in the inventory. Use field names, formats, generic storage paths, public binary hashes and sanitized test receipts. Investigations of uncertain outbound behavior stay in the established sacrificial-account/offsite setup described in [AGENTS.md](../AGENTS.md#privacy-investigations-and-test-identities).
